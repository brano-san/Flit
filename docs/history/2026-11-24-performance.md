# Оптимизация Flit перед 1.0

База сравнения — `v0.12.1` (`74ade8d7`). Наборы данных синтетические и повторяют типичные пользовательские нагрузки. В проверках использовались код Flit, реальные временные файлы и обычный путь обработки событий GUI.

## Папки и навигация

| Сценарий | Изменение |
| --- | --- |
| Открытие большой папки с сортировкой по имени | Для обычного списка без группировки рабочая запись сортировки уменьшилась с 40 до 24 байт на x86-64. При совпадении префиксов выполняется полное сравнение имён. Сортировка 100 000 имён в целевом тесте заняла 14,19 → 9,97 мс. |
| Нечёткий фильтр по именам файлов с Unicode | Фильтр сравнивает символы по мере приведения к нижнему регистру. Ему больше не требуется материализовать промежуточную строку для каждого имени. Фильтрация 100 000 имён с кириллицей заняла 6,89 → 4,25 мс. |
| Фильтрация фотографий и документов через `ext:` | Для ASCII-расширений регистр сравнивается непосредственно в исходных байтах. Целевой тест на 100 000 записях занял 7,43 → 1,93 мс. |
| Сворачивание больших сгруппированных списков | При раскладке строк принадлежность к свёрнутой группе проверяется через хеш-таблицу. Память таблицы освобождается при раскрытии всех групп. Сворачивание 4 000 групп заняло 2,92 → 1,41 мс. |
| Пересортировка папки при стабильном листинге | Обычные режимы используют готовый порядок воркера без повторной сборки списка. Дополнительные записи и глобальная группировка обрабатываются в общем порядке. |

## Поиск и индекс

| Сценарий | Изменение и результат |
| --- | --- |
| Ввод запроса по индексу из 1 млн записей | Для узкого запроса пропускается битовая карта. Для широкого результата сокращаются атомарные записи и копирование списка совпадений. `size:>32mb` 0,936 → 0,515 мс, `ext:rs;h;cpp` 3,439 → 3,077 мс, `path:src` 5,281 → 4,470 мс. Для коротких запросов по имени результаты менялись между прогонами. |
| Переход к строке 900 000 в результатах одного тома | При прямом доступе к порядку сортировки или списку совпадений предыдущие страницы не материализуются. 4,04 → 0,034 мс, примерно 6,87 МиБ записей промежуточного кэша исключено. |
| Формирование порядка «Путь» для индекса | Границы диапазонов дочерних записей и позиции для записи используют один временный массив. На 1 млн записей требуется примерно на 3,81 МиБ меньше рабочего пространства. |
| Открытие панели «Папки» в результатах | Для итогового упорядочивания выбираются 256 папок. Подсчёт по всем результатам сохраняется. 23,27 → 10,85 мс. |

## Архивы и файловые операции

| Сценарий | Изменение и результат |
| --- | --- |
| Первое открытие ZIP с 60 000 записей | Центральный каталог читается потоком. Для архива без комментариев 10,77 → 6,14 мс и 13,75 → 5,81 МиБ пиковой кучи. С 256 байтами комментария на запись 48,95 → 8,50 мс и 48,13 → 5,81 МиБ. |
| Открытие папки в уже проиндексированном архиве | Имена и ключи заимствуются из индекса. При группировке 60 000 записей с общим родителем 6,93 → 2,89 мс и 60 003 → 2 выделения памяти в части группировки. |
| Открытие и обход папок на Linux | Из `mountinfo` для списков и обхода извлекаются удалённые точки монтирования без построения общей таблицы. На 34 строках без удалённого тома время разбора 15,45 → 4,45 мкс, 277 → 0 выделений. Чтение procfs в замер не входило. |
| Расчёт одной контрольной суммы | Хеширование использует один переиспользуемый буфер и выполняется в существующем рабочем потоке. CRC32 файла 128 МиБ 17,61 → 13,36 мс и 3,00 → 1,00 МиБ пиковой кучи. |
| Копирование или перенос сотен файлов, если Linux не может применить `copy_file_range` | Буфер резервного пути переиспользуется в пределах операции. На 1 000 файлах по 4–20 КиБ при записи с ext4 в tmpfs цикл чтения и записи занял 24,21 → 10,66 мс, буфер выделился 1 000 → 1 раз. Изменения метаданных и принудительная запись на диск в замер не входили. |

## Превью, значки и профиль

| Сценарий | Изменение |
| --- | --- |
| Быстрый просмотр небольшого текста или RTF | Начальный буфер соразмерен текущему файлу. Например, для 4 КиБ текста начальная ёмкость снижается с 64 КиБ примерно до 4 КиБ. Предельный размер чтения сохранён. |
| Форматирование JSON, YAML, TOML и XML в инспекторе | Для обычного UTF-8 форматтер читает из входного буфера. Убрана копия строки размером с документ. Для BOM и UTF-16 сохранена обработка, проверенная тестом. |
| Запись миниатюр при просмотре папки с изображениями | Заголовок и пиксели записываются из двух срезов, без копии растрового блока до 1 МиБ на запись. В повторном парном замере Windows запись 64 миниатюр размером 512×512 заняла 25,02 → 16,25 мс. Суммарно выделено 67 120 078 → 10 166 байт. |
| Прогретый запуск и обновление кэша значков | UI и поток записи делят один растр, а файл кэша кодируется в один результирующий буфер. Формат файла проверен побайтово. |
| Запись сеанса с несколькими окнами и панелями | Состояние и хвосты совместимости сериализуются одним проходом. Отдельные выходные буферы для каждого блока убраны. Проверена побайтовая совместимость. |
| Сохранение каталога тегов после массовой правки | Сериализатор работает со ссылкой на хранилище. Таблица файлов, пути и теги больше не клонируются целиком перед записью. |

## Методика

Папки замерялись в Criterion на Windows с привязкой к одному логическому процессору и одним потоком Rayon. Для обеих версий использовались одинаковые сценарии из `crates/flit-core/benches/core.rs` и по 15 измерений. При параллельных сборках время сортировки и сворачивания групп сильнее зависело от нагрузки, поэтому приведены результаты менее загруженного прогона.

Микрозамеры поиска использовали 1 млн записей, 8 рабочих потоков Rayon и одинаковые сборки зависимостей. Числа в миллисекундах показывают время отдельной операции движка. Файловые замеры проводились в WSL с прогретым кэшем и чередованием базовой и новой сборок. Пик кучи и количество выделений измерялись внутри указанных операций. Для миниатюр указаны медианы девяти чередующихся прогонов Windows с временным кэшем. Время записи при параллельных сборках варьировалось, поэтому числа не описывают производительность на загруженном диске.

Штатный `--metrics` воспроизводит открытие папки, прокрутку, сортировку, фильтрацию и поиск в окне Flit. Сценарии и настройки запуска описаны в [методике замеров](../metrics.md).

## Сквозной прогон окна

WSL2, Xvfb, программный OpenGL, профиль сборки `measure`. Значения — медианы трёх чередующихся прогонов каждой сборки на одинаковых папках с отдельными каталогами профиля. Время указано в миллисекундах.

| Сценарий | 10 000 файлов | 100 000 файлов |
| --- | ---: | ---: |
| Запуск до первого кадра | 182,19 → 203,68 | 242,92 → 194,46 |
| Перечитывание папки до первого списка | 7,96 → 6,86 | 15,75 → 13,75 |
| Перечитывание папки до полного списка | 20,55 → 19,66 | 248,80 → 165,94 |
| Сортировка | 0,73 → 0,63 | 12,69 → 13,22 |
| Ввод символа в фильтр, медиана | 2,75 → 2,67 | 3,36 → 3,05 |
| Ввод символа в индексированный поиск, медиана | 5,84 → 5,81 | 6,45 → 5,21 |
| Ввод символа в рекурсивный поиск папки, медиана | 12,93 → 10,82 | 129,30 → 136,94 |
| Пропущенные кадры прокрутки | 0 → 0 | 0 → 0 |

Результаты запуска, сортировки и рекурсивного поиска заметно варьировались между прогонами. По трём парам нельзя утверждать, что эти сценарии стабильно ускорились или замедлились. Полный Windows GUI-прогон базовой версии в этой среде периодически завершался по таймауту. Сопоставимых сквозных чисел Windows нет.

В Weston обе сборки прошли тот же сценарий. Единичный контрольный прогон показал одинаковое число интервалов, отмеченных как пропущенные кадры: 124 на 10 000 файлов и 128 на 100 000. Эти числа относятся к headless-композитору с программным рендерингом.

## Проверки

- Windows — 2 301 тест рабочей области прошёл, 63 штатно пропущены. Строгий Clippy прошёл.
- Linux в WSL — 2 631 тест рабочей области прошёл, 46 штатно пропущены. Строгий Clippy с функцией `flit-platform-linux/agent` прошёл.
- Сценарии AT-SPI в Xvfb прошли. Проверки архитектурных слоёв, изоляции Windows-зависимостей и форматирования прошли.
