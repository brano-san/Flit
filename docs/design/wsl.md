# WSL во Flit

Статус: этап 4 реализован. Папки WSL открываются через агента `flit-wsl-agent` (§5), который Flit сам доставляет в дистрибутив и запускает по первому действию пользователя; упрощённый режим через `\\wsl.localhost` остался запасным путём (§4, §7). Копирование и перемещение внутри дистрибутива (§9) и поиск внутри дистрибутива (§10) не сделаны.

Пометки: **[код Flit]** — так работает текущий код; **[реестр]** — наблюдалось read-only на машине разработки (Windows 11 25H2, 26200.9711, один дистрибутив Ubuntu-22.04, WSL2); **[измерено]** — проверено на той же машине игнорируемыми тестами `crates/flit-platform-windows/test/wsl.rs` (запуск: `cargo test -p flit-platform-windows --release -- --ignored`); **[гипотеза]** — не проверялось.

## 1. Цель

Каталоги дистрибутивов WSL — полноправные расположения Flit:

- листинг со скоростью Linux-нативного кода;
- точные имена Linux (любые байты, кроме `/` и NUL);
- живые обновления через inotify;
- корзина по спецификации freedesktop;
- остановленные дистрибутивы не будятся без действия пользователя.

## 2. Модель пути

### 2.1 Формы

| Форма | Пример | Где используется |
|---|---|---|
| `wsl://<distro>/<путь Linux>` (канон) | `wsl://Ubuntu-22.04/home/u/src` | `Location::to_bytes`, сохранённое состояние, протоколы, адресная строка, `Location::display` |
| `\\wsl.localhost\<distro>\…` | `\\wsl.localhost\Ubuntu-22.04\home\u\src` | `to_windows()`: всё, что идёт в Win32 и Shell (ShellExecute, `IFileOperation`, NtFs в упрощённом режиме) |
| `\\wsl$\<distro>\…` | `\\wsl$\Ubuntu-22.04\etc` | только на входе (старая форма) |
| `\\?\UNC\wsl.localhost\…` | — | на входе; NtFs открывает каталоги verbatim-путями (`to_wide(true)`) |

### 2.2 Правила разбора [код Flit, `location.rs`]

- Схема `wsl://` без учёта регистра. Имя дистрибутива — до первого `/`, проверяется `valid_distro`: `[A-Za-z0-9._-]{1,64}`, не `.` и не `..` (§11). Без пути подставляется `/`. `wsl:///etc` отвергается.
- Путь — `FsPath` вида `Unix`: `.` и пустые сегменты выбрасываются, `..` схлопывается лексически и выше `/` не поднимается.
- `from_local`: хосты `wsl.localhost` и `wsl$` (без учёта регистра, включая verbatim `\\?\UNC\…`) с допустимым именем дистрибутива дают `Location::Wsl`, любой другой UNC остаётся `Location::Local`.
- `Location::canonicalize` приводит имя дистрибутива к написанию из реестра; `App::dispatch` вызывает его для каждого перехода.
- Строка дистрибутива в «Этом компьютере» (`Location::computer().join(b"Ubuntu-22.04")`) открывает `wsl://Ubuntu-22.04/`.
- `to_windows()` всегда выдаёт `\\wsl.localhost\`.
- Родитель корня дистрибутива — «Этот компьютер». Крошки: `This PC › Ubuntu (WSL) › home › u`.
- `Location::provider()` возвращает `ProviderId::Wsl(distro)`.

### 2.3 Экранирование имён в представлении Windows

| Байт в имени Linux | Символ в имени Windows |
|---|---|
| 0x01–0x1F | U+F001–U+F01F |
| `"` `*` `:` `<` `>` `?` `\` `\|` | U+F000 + код (`:` → U+F03A) |
| всё остальное | без изменений (UTF-8 → UTF-16) |

Обратно (`from_local`) U+F001–U+F07F декодируются только для перечисленных байтов. Схема совпадает с той, которой WSL обозначает такие имена [измерено: файл `a:b`, созданный в Linux, NtFs видит через `\\wsl.localhost` как `a` U+F03A `b`, тест `share_names_and_notifications`]. Модельно её покрывает тест `linux_names_with_windows_forbidden_chars`. Агент присылает настоящие имена Linux, поэтому вне упрощённого режима экранирование нужно только для путей, уходящих в Win32 (`to_windows()`).

### 2.4 Что не представимо в Windows

| Случай | Канон | Представление Windows | Последствие |
|---|---|---|---|
| невалидный UTF-8 (`bad\xFF`) | без потерь: сырые байты в `wsl://…` | `to_windows()` = `None` | показывается с U+FFFD; в упрощённом режиме недоступно; агент работает |
| имя с настоящим символом U+F03A | без потерь | совпадает с экранированным `:` | `from_local` превращает его в `:`, это уже другой файл (коллизия упрощённого режима) |
| имя оканчивается точкой или пробелом | без потерь | Win32 срезает их при нормализации не-verbatim путей | NtFs листает verbatim-путём и видит верно, но ShellExecute и `SHCreateItemFromParsingName` (`to_wide(false)`) адресуют другой файл, поэтому `ShellCom::open` и `ShellCom::trash` такие пути отвергают с ошибкой (исправлено; раньше «Удалить» для `build.` удалило бы `build`) |
| зарезервированные имена (`con`, `nul.txt`) | без потерь | как есть | [измерено] NtFs листает `con`, `nul.txt`, `dot.` и `space ` через `\\wsl.localhost` под их настоящими именами; адресация не-verbatim путями не проверялась |
| NUL | в именах Linux не бывает; `FsPath` его отвергает (исправлено) | Win32 обрезает путь | §11 |

## 3. Провайдеры

Как устроено [код Flit]:

- `flit_platform::Provider { fn submit(&self, req: ProviderRequest) }` асинхронный. Ответы приходят через канал `ProviderEvent`, листинги — через `SnapshotSlot`.
- `ProviderId::{Local, Wsl(distro)}` получается из `Location::provider()`.
- `App` выпускает `Effect::Provider { provider, req }` по `Location` вкладки. Отдельного поля «провайдер» у `Tab` нет, он выводится из `Location`, поэтому переход `C:\` → `wsl://…` в той же вкладке сам меняет провайдера.
- `Handler::submit` (`crates/flit/src/app.rs`) — единственная развилка: `Local` → `LocalProvider`, `Wsl(d)` → `WslProvider` этого дистрибутива из `wsl: HashMap<String, WslProvider>`. Провайдер создаётся лениво при первом запросе, имя дистрибутива сначала приводится к написанию из реестра (список кэшируется и обновляется вместе с местами), поэтому `\\wsl$\ubuntu-22.04` и `wsl://Ubuntu-22.04` попадают в одного провайдера.
- `WslProvider` (`crates/flit-platform/src/wsl.rs`) прячет агента за `AgentLauncher` (запуск и доставка; реализация Windows — `WslLauncher` в `flit-platform-windows`) и сам откатывается на `via_unc` + `LocalProvider`, когда агента нет. Без встроенного бинарника нужной архитектуры (`Platform::wsl_launcher` вернул `None`) провайдер сразу работает в упрощённом режиме.
- Агенту уходят `List`, `Watch`, `DirSizes` и `Op::Trash`; корзину в папке WSL UI адресует `ProviderId::Wsl` с путями Linux (`delete_with` в `ui/ops.rs`). Всё прочее, что приходит в `WslProvider`, идёт через `via_unc`, а непредставимый в Windows путь в операции даёт `OpDone` с ошибкой `UNMAPPABLE`. Остальные файловые операции (копирование, перемещение, переименование, «Удалить навсегда») UI по-прежнему отправляет `LocalProvider` с путями `\\wsl.localhost` (§9).
- События возвращаются по `TabId` + `gen` (`window_of_tab`, `TAB_STRIDE`).
- Linux-сборка Flit может использовать тот же код `flit-platform-linux` (`LinuxFs`, `Inotify`, `Trash`) напрямую. Агент — это тот же код, только за каналом.

## 4. Стадия 1: упрощённый режим

`via_unc` переписывает все пути запроса в `\\wsl.localhost\<distro>\…` и отдаёт запрос `LocalProvider` (NtFs, DirWatcher, ShellCom). С этапа 4 это запасной путь: без встроенного агента, после неудачного запуска или доставки и после трёх падений (§7).

| Ограничение | Причина |
|---|---|
| Имена с запрещёнными в Windows символами показываются символами U+F0xx; канонический путь вкладки содержит U+F0xx вместо исходных символов | имена приходят из представления Windows. Обратное преобразование через `to_windows()` работает, но «Копировать путь» выдаёт не настоящее имя Linux |
| Нет живых обновлений | [измерено] `ReadDirectoryChangesW` на `\\wsl.localhost` не присылает событий ни для записи из Windows, ни для записи из Linux; обновление только по F5 и после операций Flit |
| Скорость | [измерено] 10 000 пустых файлов NtFs листает за 13,4 мс (медиана), агент — за 8,5 мс. Медленный или только стартующий дистрибутив занимает воркеры общего пула `LocalProvider` (`FS_THREADS` = 4) и задерживает локальные листинги |
| Первое обращение будит дистрибутив | [измерено] холодный старт ВМ WSL2 около 2,8 с, запуск `wsl.exe` для работающего дистрибутива около 84 мс |
| Точечные файлы не скрываются | [гипотеза] 9P не ставит `FILE_ATTRIBUTE_HIDDEN` |
| Абсолютные символические ссылки Linux | [гипотеза] из Windows не разрешаются |
| Невалидный UTF-8, имена с точкой или пробелом на конце, коллизия U+F0xx | §2.4 |
| Регистр | `App.case` по умолчанию `Insensitive`, а в Linux `A` и `a` — разные файлы (§12) |

Найдено при подготовке документа:

1. **Исправлено.** Раньше `via_unc` при `to_windows() == None` (невалидный UTF-8) отдавал запрос `LocalProvider` с исходным Unix-путём, и Win32 читал `/tmp/x` как `C:\tmp\x`. Теперь `via_unc` возвращает `Option`: `List` сразу получает снимок с ошибкой `Unavailable`, `Watch` снимает слежение, `DirSizes`, `Op::Trash` и `Open` отбрасываются (тест `unmappable_wsl_paths_never_reach_win32`).
2. **Исправлено.** `ShellCom::trash` и `ShellCom::open` отказываются от путей, где есть имя на точку или пробел. Это касается и локальных путей NTFS, не только WSL.
3. **Исправлено.** NUL в `FsPath` (§11).
4. Желательно: прогонять имена из листинга через обратное экранирование до `Location::join`. Тогда канонический путь будет содержать настоящие имена Linux, а сохранённые в упрощённом режиме вкладки останутся верными и для агента.

## 5. Агент `flit-wsl-agent`

### 5.1 Сборка и встраивание

- `[[bin]] flit-wsl-agent` в `flit-platform-linux` с `required-features = ["agent"]`, без нового крейта: `LinuxFs`, `Inotify`, `Trash` и `flit-proto`. Весь крейт под `#![cfg(target_os = "linux")]`, на Windows он пуст.
- Цели `x86_64-unknown-linux-musl` и `aarch64-unknown-linux-musl`; бинарник статический, профиль `wsl-agent` (release, `strip = true`, без отладочной информации), около 650 КБ. Архитектура выбирается по родной архитектуре Windows (`native_arm64` через `IsWow64Process2`), потому что дистрибутив совпадает с ней.
- Без зависимостей на C, кроме `libc` (только объявления); линкуется `rust-lld` прямо с Windows (`.cargo/config.toml`) [измерено].
- Сборочный скрипт `crates/flit/build.rs` берёт готовые файлы из `FLIT_WSL_AGENT_X64` и `FLIT_WSL_AGENT_ARM64`. Если переменной нет, а цель musl установлена, он сам собирает агента вложенным `cargo build --locked --profile wsl-agent --target <musl>` в `<target>/wsl-agent` (так собирается только x64). Файлы встраиваются через `include_bytes!` в `AGENTS: AgentImages`; нет файла — для этой архитектуры остаётся только упрощённый режим, а сборка печатает `cargo:warning`.
- Идентификатор агента: `<версия>-<первые 16 hex SHA-256 бинарника>` (`flit_proto::build_id`). `build.rs` считает его от встраиваемого файла, сам агент — от `/proc/self/exe` при старте, так что совпадение в `Hello` означает тот же файл.
- musl не даёт обёртки `statx`, поэтому агент зовёт системный вызов напрямую со своей структурой `Statx`, а каталоги читает через `getdents64`.

### 5.2 Доставка и запуск

Агент лежит в `${XDG_CACHE_HOME:-$HOME/.cache}/flit/agent-<id>`, каталог с правами 0700.

Тёплый путь — один запуск процесса:

```text
%SystemRoot%\System32\wsl.exe -d <distro> --exec /bin/sh -c 'exec "${XDG_CACHE_HOME:-$HOME/.cache}/flit/agent-<id>"'
```

`--exec` обходит login shell пользователя, `$HOME` раскрывает `sh`, а `exec` отдаёт агенту stdio напрямую. Абсолютный путь к `wsl.exe` защищает от подмены через `PATH` и текущий каталог.

Если `Hello` не пришёл (файла нет: `sh` пишет ошибку в stderr и выходит с кодом 127, stdout пуст, значит EOF), выполняется доставка с бинарником в stdin, затем ещё одна попытка тёплого пути:

```text
wsl.exe -d <distro> --exec /bin/sh -c 'set -e; d="${XDG_CACHE_HOME:-$HOME/.cache}/flit"; mkdir -p "$d"; chmod 700 "$d"; t="$d/agent-<id>.$$"; cat > "$t"; chmod 700 "$t"; mv -f "$t" "$d/agent-<id>"'
```

Не через `\\wsl.localhost`: так не нужно знать `$HOME`, нет 9P и не остаётся полузаписанных файлов (атомарный `mv`).

`wsl.exe` запускается с `CREATE_NO_WINDOW` в Job object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Если `flit.exe` упадёт, `wsl.exe` завершится, агент получит EOF на stdin и выйдет, и дистрибутив сможет остановиться по простою [измерено: после завершения `wsl.exe` процесс агента исчезает, тест `killing_wsl_exe_ends_the_agent`]. Процесс попадает в Job сразу после `spawn`, а не созданным приостановленным: std не умеет `CREATE_SUSPENDED`, и окно в несколько микросекунд оставлено.

Замеры [измерено]: доставка 650 КБ — 82–91 мс; тёплый запуск от `spawn` до `Hello` — медиана 45 мс; первый листинг через новый `WslProvider` с уже доставленным агентом — 50–63 мс.

### 5.3 Транспорт и Hello

- stdin и stdout `wsl.exe`, кадры `u32` LE + postcard (`flit-proto/src/transport.rs`), `MAX_FRAME` = 16 МиБ. stderr агента пишется в лог Flit.
- Обе стороны сразу шлют `Hello`: `{ magic: "FLIT", protocol: Provider, version: provider::VERSION (= 2), build }`, где `build` — идентификатор из §5.1. Агент пишет свой `Hello` первым, не дожидаясь чужого.
- Мусор вместо `Hello` (сообщение `wsl.exe` в UTF-16, предупреждения) даёт `NotFlit`; это покрыто тестом `handshake_errors_are_specific`.
- `NotFlit`, `VersionMismatch`, EOF или чужой `build` → одна доставка и повторный запуск, иначе упрощённый режим для этого дистрибутива.
- `VERSION` повышается при любом изменении сообщений: postcard не самоописываемый. Версия 2 сменила `OpDone.error` на текст.
- stdio `wsl.exe` двоично прозрачен: байты 00 0A 0D 0A FF 1A проходят без изменений [измерено, тест `wsl_stdio_is_binary_transparent`]. stderr `wsl.exe` может прийти в UTF-16LE, `decode` различает кодировку по наличию нулевых байтов.

### 5.4 Сообщения (`crates/flit-proto/src/provider.rs`)

| Запрос UI (`ProviderRequest`) | Агенту (`Request`) | От агента (`Event`) | В UI |
|---|---|---|---|
| `List { tab, gen, path, view, case, out, cancel }` | `List { id, path }` | `Entries { id, batch }`…, `ListDone { id, error }` | `EntryBatch::append_to` → `Listing`; `DirSnapshot` в `out` каждые 16 мс и в конце, как в `local::list`; сортировка на стороне Windows |
| `Watch { tab, gen, Some(path) }` | `Watch { id, path }` | `Changes { id, changes }`, `Rescan { id }` | `ProviderEvent::Changes` / `Rescan { tab, gen }` |
| `Watch { tab, gen, None }` | `Cancel { id наблюдения }` | — | — |
| `DirSizes { tab, gen, dir, items, cancel }` | `DirSizes { id, dir, items }` | `DirSize { id, idx, size }` | `ProviderEvent::DirSize` |
| `Op { id, op: Trash(paths) }` | `Op { id, op }` | `OpDone { id, error }` | `ProviderEvent::OpDone` |
| `Open { path }` | — | — | ShellExecute для `to_windows()` (§8) |
| — | `Stat { id, path }` | `Stat { id, result }` | агент отвечает, но UI запрос пока не шлёт (проверка пути из адресной строки идёт через листинг) |
| простой или выход | `Shutdown` | — | — |

Отмена. `WslProvider` проверяет `GenToken` на каждом входящем `Entries` и `DirSize`. Если запрос устарел, агенту уходит один `Cancel { id }`, дальнейшие события с этим `id` отбрасываются. Агент проверяет набор отменённых `id` между пачками записей и между каталогами в `DirSizes`; `Cancel` с `id` наблюдения снимает наблюдение.

Потоковая выдача: пачка `Entries` раз в 16 мс (проверяется каждые 64 записи) или по 4096 записей, что наступит раньше. На 10 000 записей это 8,5 мс на весь листинг (медиана), в живом `flit.exe` первые строки через 8,4 мс и полный листинг через 12,7 мс [измерено]. Каждый листинг, `DirSizes` и операция обслуживаются отдельным потоком агента, ответы пишет один поток с буфером 1 МиБ.

Каждое событие агента проходит `Event::validate` до того, как попадёт в UI; невалидное событие считается разрывом связи (§7, §11).

### 5.5 Метаданные

| Поле `Meta` | Источник в Linux |
|---|---|
| `size` | `st_size` |
| `modified` | mtime из `statx` → такты FILETIME: (секунды + 11 644 473 600) × 10⁷ + наносекунды / 100 (как ожидает `fmt::datetime`) |
| `created` | btime при `STATX_BTIME`, иначе 0 |
| `DIR` | `S_ISDIR`; для ссылки — по цели, вместе с `LINK` |
| `LINK` | `S_ISLNK` |
| `HIDDEN` | имя начинается с `.` |
| `READONLY` | `mode & 0o222 == 0` |

WSL1: `statx` может вернуть `ENOSYS`, тогда используется `fstatat` (без btime). WSL1 не проверялся.

### 5.6 Наблюдение (inotify)

- Маска: `IN_CREATE`, `IN_DELETE`, `IN_MOVED_FROM`, `IN_MOVED_TO`, `IN_MODIFY`, `IN_ATTRIB`, `IN_CLOSE_WRITE`, `IN_DELETE_SELF`, `IN_MOVE_SELF`, `IN_ONLYDIR`.
- События склеиваются за 50 мс в `Changes`. Изменение определяется по состоянию на момент сброса: имя, которое существует, приходит как `Added` с метаданными `statx`, исчезнувшее — как `Removed`. UI обрабатывает `Added` для уже показанного имени как обновление. Задержка от записи через 9P до `ProviderEvent::Changes` — 49,4 мс, то есть почти целиком окно склейки [измерено].
- Наблюдения разделяют один дескриптор наблюдения на каталог, сколько бы вкладок его ни смотрели.
- `IN_Q_OVERFLOW`, `IN_DELETE_SELF`, `IN_MOVE_SELF`, `IN_IGNORED` → `Rescan`.
- `ENOSPC` (исчерпан `max_user_watches`) → наблюдения нет, запись в лог.
- Изменения, сделанные Windows в `/mnt/c` (DrvFs), inotify не видит. Такие пути лучше открывать как локальные (§12).

### 5.7 Корзина (freedesktop Trash 1.0)

- Файл на устройстве домашней корзины идёт в `$XDG_DATA_HOME/Trash` (по умолчанию `~/.local/share/Trash`). Иначе — в `$topdir/.Trash/$uid`, если `.Trash` — каталог со sticky bit и не ссылка, иначе в `$topdir/.Trash-$uid` (создаётся с правами 0700).
- Сначала `info/<имя>.trashinfo` создаётся с `O_CREAT | O_EXCL` (при конфликте `<имя>.2`, `<имя>.3`, …). Содержимое: `[Trash Info]`, `Path=` (percent-encoded; абсолютный путь для домашней корзины, относительно `$topdir` для остальных), `DeletionDate=YYYY-MM-DDThh:mm:ss` по местному времени. Затем `rename(2)` в `files/<имя>`. Если `rename` не удался, `.trashinfo` удаляется и возвращается ошибка.
- Копирования между устройствами нет: при `EXDEV` приходит `OpDone` с ошибкой, а UI может предложить удаление без корзины.
- Кэш `directorysizes` не ведётся.
- Корзина Linux не попадает в журнал отмены Flit: агент не сообщает, куда положил файл, и `OpReport` приходит без элементов. Вернуть файл можно средствами Linux (`gio trash --restore`, файловый менеджер).
- В Ubuntu-22.04 под WSL2 `/tmp` лежит на том же устройстве, что и домашний каталог, поэтому тестовые файлы из `/tmp/flit-*` уходят в `~/.local/share/Trash` [измерено].

### 5.8 Размеры каталогов

Обход через `getdents64` и `statx(AT_SYMLINK_NOFOLLOW)`, ссылки не разыменовываются, суммируется `st_size`, отмена проверяется на каждом каталоге, каталоги считаются пулом потоков. Семантика та же, что у `tree_size` в `local.rs`: ссылка на каталог даёт 0. Имена из `DirSizes.items`, не прошедшие проверку §11, получают размер 0 и запись в лог.

## 6. Обнаружение дистрибутивов

Источник — `HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss`. В корне `DefaultDistribution` (GUID), в подключах `{GUID}`:

| Значение | Смысл | На этой машине [реестр] |
|---|---|---|
| `DistributionName` | имя для `-d` и для `wsl://` | `Ubuntu-22.04` |
| `Version` | 1 = WSL1, 2 = WSL2 | 2 |
| `State` | 1 = установлен; другие значения (установка, удаление, конвертация) пропускаются | 1 |
| `BasePath` | каталог дистрибутива | `D:\WSL\Ubuntu-22.04` |
| `DefaultUid` | пользователь по умолчанию | 1000 |
| `Flags` | interop, `PATH`, монтирование дисков, WSL2 | `0xF` |
| `VhdFileName` | диск WSL2 | `ext4.vhdx` |
| `Flavor`, `OsVersion` | подпись | `ubuntu`, `22.04` |

- Чтение реестра дистрибутивы не будит. `places::wsl_distros` берёт подключи с `State = 1` и допустимым именем (§11). Поток `flit-lxss-watch` ждёт `RegNotifyChangeKeyValue` (имена и значения, с подключами) на `Lxss`, открытом с `KEY_NOTIFY`, и просит воркер мест перечитать список; реестр Flit только читает.
- «Этот компьютер» после дисков показывает дистрибутивы из реестра строками-папками (`DIR | VOLUME`, без размера) → `wsl://Ubuntu-22.04/`; в боковой панели они, как и раньше, в разделе WSL с глифом Linux. Значок строки в «Этом компьютере» — значок ярлыка дистрибутива из меню «Пуск» (значение `ShortcutPath` в реестре; у Ubuntu-22.04 он указывает на `%LOCALAPPDATA%\wsl\{GUID}\shortcut.ico`). Запрос значка для `\\wsl.localhost\<d>\` `ShellCom::icon` никогда не передаёт оболочке, иначе показ «Этого компьютера» запускал бы дистрибутив; нет ярлыка (дистрибутивы из Store) — остаётся глиф.
- Без действия пользователя — никаких обращений к `\\wsl.localhost\<distro>` и запусков `wsl.exe -d`: и то и другое запускает дистрибутив. Агент запускают только `List`, `DirSizes` и `Op::Trash` (наблюдение без листинга ждёт в очереди), а их порождают переход, F5 или операция. Открыть строку дистрибутива значит согласиться на запуск; пока агент стартует, строка состояния вкладки вместо «Loading…» показывает «Starting Ubuntu-22.04…» (`ProviderEvent::Status`). Вкладка WSL, восстановленная при запуске Flit, тоже запускает дистрибутив: восстановление считается действием пользователя.
- WSL1: файлы под `BasePath\rootfs` никогда не трогать напрямую, только через `\\wsl.localhost` или агента.
- Имя дистрибутива в `Location` приводится к написанию из реестра (сравнение без учёта регистра): `\\wsl$\ubuntu-22.04` открывает `wsl://Ubuntu-22.04/` и того же провайдера. Вкладки, восстановленные до первого чтения мест, получают написание из реестра в `Handler`, а сам `Location` — при следующем переходе.
- Признак «дистрибутив запущен» не показывается: `wsl.exe --list --running` не вызывается, чтобы не трогать службу WSL без действия пользователя.

## 7. Жизненный цикл агента

| Состояние | Что происходит | Переходы |
|---|---|---|
| Нет агента | исходное | первый запрос к `wsl://<d>`, вызванный действием пользователя → Запуск |
| Запуск | тёплый путь (§5.2); запросы копятся в очереди | `Hello` принят → Готов, очередь уходит агенту; `NotFlit`, чужой `build` или EOF → Доставка (один раз); нет `Hello` за 15 с → Упрощённый |
| Доставка | запись бинарника | успех → Запуск; ошибка → Упрощённый |
| Готов | обслуживание запросов | 5 мин без наблюдений и незавершённых запросов → Остановка; EOF, ошибка ввода-вывода или невалидное событие → Упал |
| Остановка | `Shutdown`, закрыть stdin, ждать 1 с, затем завершить `wsl.exe` | → Нет агента |
| Упал | листинги получают снимок с ошибкой `Unavailable`, операции — `OpDone` с ошибкой, вкладки с наблюдением — сообщение «The connection to <d> was lost: this folder no longer updates. Press F5 to reload it.» | следующий запрос от действия пользователя (навигация, F5) → Запуск; 3 падения за 5 мин → Упрощённый |
| Упрощённый | `via_unc` + `LocalProvider` | до перезапуска Flit |

Сроки собраны в `flit_platform::Timing` (тесты подставляют миллисекунды). Тайм-аут `Hello` в 15 с с запасом покрывает холодный старт ВМ (около 2,8 с [измерено]).

Автоматического перезапуска после падения нет. Пользователь мог сам остановить дистрибутив (`wsl --terminate`, `wsl --shutdown`), а восстановление наблюдений разбудило бы его снова. Наблюдения возвращаются только после перезапуска, который вызвал пользователь.

Агент живёт, пока открыт stdin: EOF — выход. Работающий агент держит дистрибутив запущенным, поэтому остановка по простою важна для памяти и батареи.

## 8. Открытие файлов

| Действие | Механизм | Ограничения |
|---|---|---|
| Enter, двойной щелчок | ShellExecuteEx для `to_windows()`; приложение Windows по ассоциации читает файл через 9P | непредставимое имя → ошибка «имя не представимо в Windows»; имя с точкой или пробелом на конце → отказ |
| «Открыть в Linux» (стадия 2) | агент запускает `xdg-open` с сырыми байтами пути (новый `Request::Open { id, path }`); GUI Linux показывается через WSLg | через `wsl.exe` с путём в argv нельзя: argv у `wsl.exe` UTF-16, невалидный UTF-8 не передать |
| «Терминал здесь» | `wsl.exe -d <distro> --cd <путь Linux>` | только пути в UTF-8 |
| Исполняемый файл Linux | ShellExecute его не запустит | только «Открыть в Linux» или терминал |

## 9. Копирование и перемещение

Не сделано на этапе 4. Копирование, перемещение, переименование, создание и удаление в папках WSL идут через движок Windows по `\\wsl.localhost` (отклонение 30 в ARCHITECTURE.md); агент выполняет только `Trash`, на остальные `FileOp` отвечает ошибкой. План:

| Направление | Механизм | Почему |
|---|---|---|
| Windows ↔ WSL | движок копирования Windows (`IFileOperation` или `CopyFileEx`) по `\\wsl.localhost\…` | прогресс, конфликты и отмена как у локальных операций; скорость 9P |
| внутри одного дистрибутива | агент: `rename(2)`, иначе `copy_file_range`; новые варианты `FileOp` (`Copy`, `Move`, `Rename`, `Mkdir`, `Delete`), общие для `LocalProvider` и агента | намного быстрее 9P; сохраняются права, владелец и ссылки, которые 9P теряет [гипотеза] |
| между дистрибутивами | через Windows (9P на обоих концах) | редкий случай |
| имена, непредставимые в Windows | только агентом; на стороне Windows — ошибка с именем файла | 9P такие имена не адресует |

## 10. Поиск

- Служба индекса и агент делят тип `EntryBatch` (`flit-proto/src/listing.rs`; в `flit-search/src/proto.rs` — `Message::Rows { entries: EntryBatch, dirs }`).
- Рекомендация: индекс дистрибутива ведёт сам агент внутри дистрибутива (`WalkIndex` из `flit-platform-linux` + inotify) и отвечает по протоколу `flit-search` (`Query`, `GetRows`, `Rows`, `IndexStatus`). Это второй процесс агента с `Hello { protocol: Index }`, запущенный тем же способом. Поиск Flit объединяет ответы `flit-indexd` (тома Windows) и агентов, добавляя к `dirs` префикс `wsl://<distro>`.
- Почему не стримить обход в `flit-indexd`: при каждом старте дистрибутива через канал шли бы миллионы записей, служба индекса будила бы дистрибутивы, а изменения всё равно видны только изнутри (inotify).
- Участвуют только запущенные дистрибутивы; поиск их не будит.
- `\\wsl.localhost` не является томом NTFS и в MFT-индекс не попадает; `ext4.vhdx` индексируется как обычный файл.

## 11. Безопасность

Граница доверия — канал агента. Дистрибутив может быть скомпрометирован, а имена файлов Linux всегда приходят из внешних источников (архивы, git). Всё, что прислал агент, проверяется:

- кадры не больше 16 МиБ, `Hello` не больше 256 байт, иначе разрыв;
- `EntryBatch::entries()` отвергает пустые имена, `.`, `..`, имена с `/` или NUL и несовпадение длин, включая переполнение суммы;
- `FsPath` при декодировании отвергает относительные пути, а `..` схлопывается лексически и за корень не выходит;
- имена в `Event::Changes` (`DirChange.name`) проверяются так же, как в `EntryBatch` (исправлено: `Event::validate`; `WslProvider` прогоняет через него каждое событие, и невалидное рвёт связь);
- `FsPath::parse_exact` отвергает NUL (исправлено, `external-open.md`, §7.4).

Остальное:

- Агент тоже проверяет вход: путь должен быть вида `PathKind::Unix` (`fs::host`), имена в `DirSizes.items` проверяются по тем же правилам, а NUL не пройдёт через `CString`.
- Имена Linux с `\` и `:` законны и передаются как есть. Путь Windows никогда не собирается склейкой строк, только как `Location::Wsl.join(name).to_windows()`.
- Имя дистрибутива берётся из реестра и при разборе `wsl://` и `\\wsl$` ограничено набором `[A-Za-z0-9._-]` длиной до 64 символов, без `.` и `..` (`location::valid_distro`, исправлено). Тот же фильтр применяется к списку из реестра, поэтому в `wsl.exe -d` и в `\\wsl.localhost\<distro>` попадают только такие имена. Дистрибутив с другим именем Flit не показывает.
- Канал — stdio дочернего процесса: ни TCP, ни Unix-сокетов, ни сокетов в файловой системе, другой процесс к агенту не подключится.
- Агент работает от пользователя дистрибутива по умолчанию, без повышения прав. Доступа к Windows у него не больше, чем у любого процесса Linux с interop.
- Файл агента в `~/.cache/flit` (0700) может подменить только тот, кто уже владеет учётной записью Linux; новых прав это не даёт. Подмену выявит `Hello` (идентификатор сборки), а данные всё равно проходят проверки выше.
- `wsl.exe` и `explorer.exe` запускаются по абсолютному пути из `%SystemRoot%`.
