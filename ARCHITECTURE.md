# Архитектура Flit

Документ описывает устройство этапа 1. Пользовательская сторона — в [README.md](README.md), подробные проектные записки — в [docs/design/external-open.md](docs/design/external-open.md) и [docs/design/wsl.md](docs/design/wsl.md), замеры — в [docs/metrics.md](docs/metrics.md).

Три принципа, из которых следует остальное:

1. **Ядро без ввода-вывода.** Вся логика интерфейса — состояние вкладок, выделение, навигация, раскладка, построение списка примитивов для GPU — живёт в `flit-core` и не делает системных вызовов. Ядро общается с внешним миром через очередь эффектов (`Effect`) и входящие события, поэтому целиком тестируется без окна и без диска.
2. **UI-поток не ждёт.** Чтение папок, слежение за изменениями, значки, названия типов, открытие файлов, файловые операции и фоновая сортировка выполняются в рабочих потоках; результаты приходят через каналы и будят цикл сообщений.
3. **Кадр только по изменению.** Пока ничего не меняется, процесс спит в `WaitMessage`; кадр строится, когда изменилось состояние или идёт анимация, и выводится с синхронизацией по кадровому ожиданию swap chain.

## Крейты и правило зависимостей

| Крейт | Назначение | Внутренние зависимости |
|---|---|---|
| `flit-core` | имена, пути, `Location`, листинги, сортировка, `Open` и маршрутизация, вкладки и `App`, раскладка, текстовый кэш, атлас, `DrawList` | — |
| `flit-proto` | транспорт (кадры, `Hello`), протоколы единственного экземпляра и агента-провайдера, общий `EntryBatch` | `flit-core` |
| `flit-search` | типы формата индекса и протокол поиска (этап 2) | `flit-proto` |
| `flit-platform` | трейты платформы (`Platform`, `WindowSystem`, `Renderer`, `Fs`, `Watcher`, `Shell`, `FileOps`, `SingleInstance`, `IndexSource`, `Service`) и ОС-независимый `LocalProvider` | `flit-core`, `flit-search` |
| `flit-platform-windows` | реализация трейтов на Win32, D3D11 + DirectComposition, DirectWrite, NT API, Shell COM, именованных каналах | `flit-core`, `flit-proto`, `flit-search`, `flit-platform` |
| `flit-platform-linux` | заглушки, чтобы workspace собирался на Linux | `flit-core`, `flit-search`, `flit-platform` |
| `flit` | приложение: обработчик окон, рабочие потоки, сохранение состояния, сценарий метрик | `flit-core`, `flit-platform`, платформа по `cfg` |
| `flit-indexd` | служба индексации (заготовка этапа 2) | `flit-platform`, `flit-proto`, `flit-search`, платформа по `cfg` |
| `tools/flit-gen` | генератор тестовых папок | только `std` |

Слои сверху вниз: бинарники (`flit`, `flit-indexd`) → платформа (`flit-platform-windows` или `flit-platform-linux`) → `flit-platform` → `flit-core` / `flit-search` / `flit-proto`.

**Правило:** `flit-core`, `flit-proto`, `flit-search` и `flit-platform` никогда не зависят от крейтов `windows*` — ни напрямую, ни транзитивно. Код ОС есть только в `flit-platform-windows` (весь крейт под `#![cfg(windows)]`) и `flit-platform-linux`. Бинарники выбирают платформу одной строкой (`type P = flit_platform_windows::Windows` или `flit_platform_linux::Linux`), весь остальной код обобщён по `P: Platform`. CI проверяет правило задачей `deps-isolation`: для каждого из четырёх крейтов строится `cargo tree -p <крейт> -e normal,build --target all`, и сборка падает, если в дереве есть пакет, имя которого начинается с `windows`. Кроме того, Linux-задача CI собирает весь workspace и гоняет тесты ОС-независимых крейтов.

## Потоки

| Поток | Сколько | Что делает |
|---|---|---|
| главный (UI) | 1 | цикл сообщений Win32 для всех окон и скрытого окна-концентратора, `App`, раскладка, построение кадра, вызовы D3D11 |
| `flit-fs-N` | 4 | пул `LocalProvider`: задания `List` (чтение папки) из общей очереди |
| `flit-sizes` | 1 | задания `DirSizes` (размеры подпапок) по очереди, чтобы долгий подсчёт не занимал пул чтения |
| пул `rayon` | по числу ядер | параллельный подсчёт размеров подпапок, если диск не HDD |
| `flit-watch-ctl` | 1 | владеет `Watcher` и по порядку ставит и снимает слежение по командам вкладок |
| `flit-shell-N` | 2 | COM STA: значки и названия типов файлов |
| `flit-shell-ops` | 1 | COM STA: открытие файлов (`ShellExecuteExW`) и файловые операции по очереди: копирование, перемещение, переименование, новая папка, ярлыки, корзина и восстановление из неё, чтение буфера обмена для вставки |
| `flit-watcher` | 1 | порт завершения ввода-вывода (IOCP) со всеми `ReadDirectoryChangesExW` |
| `flit-sort` | 1 | фоновая пересортировка снимков при смене сортировки или фильтра скрытых |
| `flit-gpu` | 1, только при запуске | создаёт устройства D3D11: сначала программное (WARP), затем аппаратное |
| `flit-instance` | 1 | слушает именованный канал единственного экземпляра |
| `flit-instance-client` | по одному на подключение, не больше 4 одновременно | короткоживущий: рукопожатие и приём одной команды `Open` |

UI-поток не выполняет блокирующих операций с файлами и COM в обработке ввода и кадра: `Effect` превращается либо в отправку в канал, либо в дешёвый вызов Win32 (заголовок, курсор, буфер обмена). Исключения: разрешение `shell:`-путей (`Platform::known_folder`, COM) при обработке входящей команды `Open`; ожидание устройства D3D11 перед первым кадром, если `flit-gpu` ещё не создал ни одного, и пересоздание аппаратного устройства после его потери; чтение `state.bin` до создания окна и его запись при закрытии последнего окна; контекстное меню оболочки и окно свойств, объект данных и модальный цикл `SHDoDragDrop` при перетаскивании из Flit, вызовы `IDropTarget` при перетаскивании в него (см. «Файловые операции»).

Пробуждение: рабочий поток кладёт результат в канал `crossbeam` и вызывает `Wake` (`Arc<dyn Fn()>`). На Windows это `Win32Waker`: он отправляет `WM_WAKE` скрытому окну-концентратору (`HWND_MESSAGE`), а флаг `AtomicBool` схлопывает повторные пробуждения в одно сообщение. Концентратор вызывает `WindowHandler::woken` для каждого окна, и обработчик разбирает каналы.

## Загрузка папки

1. **`Tab::load(gen)`.** Вкладка получает новое поколение `gen` (счётчик `App`), записывает его в свой `GenToken`, сбрасывает очередь изменений, ошибку, хлебные крошки и статистику и выпускает два эффекта: `Effect::Provider(Watch { path })`, затем `Effect::Provider(List { gen, path, view, case, out, cancel })`. Здесь `out` — слот снимков вкладки, `cancel` — её `GenToken`. Если провайдер сменился (локальный ↔ WSL), старому уходит `Watch { path: None }`.
2. **Маршрутизация.** `Handler::flush` передаёт запрос провайдеру: `ProviderId::Local` — прямо в `LocalProvider`, `ProviderId::Wsl` — через `via_unc` (см. ниже). `Watch { path }` провайдер только запоминает за вкладкой; `List` того же поколения забирает его с собой в пул `flit-fs-N`. Рабочий поток сначала просит `flit-watch-ctl` поставить слежение и ждёт подтверждения, что запрос `ReadDirectoryChangesExW` уже выдан, и только потом читает каталог: изменение, случившееся во время чтения, не теряется. `Watch { path: None }` уходит в `flit-watch-ctl` сразу.
3. **Чтение.** `NtFs::read_dir` открывает каталог через `CreateFileW` (`FILE_LIST_DIRECTORY`, `FILE_FLAG_BACKUP_SEMANTICS`, путь с префиксом `\\?\`, поэтому длинные пути работают) и читает его `NtQueryDirectoryFile` с классом `FileIdBothDirectoryInformation` в буфер 64 КБ. Каждый заполненный буфер — одна порция: имена из UTF-16 сразу пишутся в `ListingBuilder`, который одновременно растит листинг и ключи сортировки. Для «This PC» вместо чтения каталога перечисляются диски (`GetLogicalDrives`, объём несъёмных дисков через `GetDiskFreeSpaceExW`).
4. **Публикация.** После каждой порции проверяется `GenToken`: если вкладка ушла на другое поколение, чтение прекращается. Первая порция публикуется сразу, следующие — не раньше чем через 16 мс и не раньше чем через учетверённое время предыдущей публикации: рабочий поток копирует листинг и ключи, сортирует их и публикует `DirSnapshot` в `SnapshotSlot` вкладки. Поскольку цена публикации растёт с листингом, на огромной папке промежуточных снимков становится меньше, и на копирование уходит не больше пятой части времени чтения. Перед каждой публикацией поколение проверяется снова. Слот — `ArcSwapOption<DirSnapshot>` без блокировок: новый снимок заменяет непрочитанный, но снимок старшего поколения никогда не вытесняется младшим, даже если поток прежнего задания опубликовал его позже. Финальный снимок (`done = true`, ошибка, общее время) публикуется всегда, если поколение ещё актуально. После публикации — `Wake`.
5. **Приём.** При пробуждении и в начале каждого кадра `App::poll` забирает снимки из слотов всех вкладок. `Tab::on_snapshot` отбрасывает чужое поколение, запоминает время первого и последнего снимка (они видны в строке состояния), подменяет снимок в `DirView` (выделение сохраняется: индексы растущего листинга стабильны), применяет отложенное выделение (`/select`, выход в родительскую папку) и, если за время загрузки сменилась сортировка, заказывает пересортировку.
6. **Кадр** рисует только видимый диапазон строк текущей вкладки.

### Поколения и отмена

`gen` уникален в пределах окна и всегда идёт в паре с идентификатором вкладки. `GenToken` — `Arc<AtomicU64>`, общий для вкладки и её заданий: рабочий поток спрашивает `is_current(gen)` между порциями и перед публикацией, закрытие вкладки записывает `u64::MAX`. На стороне UI устаревшие результаты отбрасываются по тем же меткам: снимок — по `gen`, события провайдера — по паре (вкладка, `gen`), результат сортировки — по тройке (вкладка, `gen`, вид).

### Слежение за изменениями

`DirWatcher` держит на каждую вкладку один дескриптор каталога, привязанный к общему IOCP, и запрос `ReadDirectoryChangesExW` с `ReadDirectoryNotifyExtendedInformation` в буфер 64 КБ. Расширенная информация уже содержит размер, времена и атрибуты, поэтому дополнительный запрос метаданных не нужен. Уведомления превращаются в `DirChange` (`Added`, `Removed`, `Modified`; переименование — `Removed` старого имени плюс `Added` нового) и уходят событием `ProviderEvent::Changes { tab, gen }`. Переполнение буфера (завершение с нулевой длиной) или ошибка дают `Rescan`, и вкладка полностью перечитывает папку с новым поколением, сохраняя фокус. Записи уведомлений разбираются из байтов по смещениям полей с проверкой границ, без приведения буфера к структуре; обрезанная или неизвестная запись отбрасывается. Если имя похоже на короткое имя 8.3 (`LONGFI~1.TXT`), поток слежения разворачивает его через `GetLongPathNameW`; для удалённого файла это невозможно, и тогда вся пачка превращается в `Rescan`. `watch(Some)` открывает каталог вне замка, а под замком привязывает его к IOCP и выдаёт первый запрос до возврата; запросы одной вкладки упорядочены по (поколение, снятие), поэтому опоздавшая постановка не перекрывает более новую команду. Смена папки отменяет старый запрос через `CancelIoEx`, дескриптор закрывается по его завершении.

На стороне UI изменения копятся в очереди вкладки. `App::frame` применяет изменения к текущей вкладке только после окончания загрузки и не дольше 4 мс за кадр (часы проверяются раз в 256 изменений); если очередь не опустела, сразу заказывается следующий кадр. Изменения применяются пачкой: `DirView::apply_all` обновляет листинг и карту имён по каждому изменению, а порядок строк перестраивает один раз на пачку. Запись, ставшая невидимой (удалена или скрыта), выходит из выделения и теряет фокус, поэтому удаление в корзину никогда не захватит то, чего нет на экране. Фоновые вкладки хранят очередь до активации; если в ней набирается больше 65 536 изменений, очередь выбрасывается и вкладка перечитывает папку, как при `Rescan`, поэтому шумная папка в фоне не растит память без предела. `DirView::apply` идемпотентен: `Added` или `Modified` для существующего имени обновляет метаданные и переставляет строку, `Added` для нового имени дописывает запись в конец листинга и вставляет строку двоичным поиском, `Removed` ставит надгробие, `Removed` для отсутствующего имени ничего не делает. Поскольку слежение поставлено до начала чтения, события, гонящиеся с чтением, ждут финального снимка, а повторное применение уже учтённого изменения безвредно. Папки WSL и UNC-шары часто не дают живых уведомлений, поэтому после успешной файловой операции такая вкладка перечитывается.

### Фоновая пересортировка

Щелчок по заголовку, Ctrl+H или устаревший вид в финальном снимке порождают `Effect::Resort { snap, view }` с `Arc` на текущий снимок. Поток `flit-sort` сортирует его и возвращает порядок вместе с длиной листинга на момент сортировки. `App::on_resorted` сверяет вкладку, поколение и вид, после чего `DirView::merge_order` выбрасывает надгробия и скрытые записи, вставляет записи, добавленные после начала сортировки, и проверяет упорядоченность; если за это время изменения сдвинули метаданные и порядок нарушен, выполняется полная сортировка на месте. До прихода результата на экране остаётся прежний порядок.

### Размеры подпапок

Ctrl+Shift+S отправляет `DirSizes` со списком видимых подпапок (без ссылок и дисков). Рабочий поток обходит каждое поддерево итеративно тем же `Fs::read_dir`, не переходя по точкам повторной обработки. Для HDD (`IOCTL_STORAGE_QUERY_PROPERTY`, `IncursSeekPenalty`) подпапки считаются последовательно, иначе параллельно через `rayon`. Задания выполняет отдельный поток `flit-sizes`. Каждый результат приходит отдельным `ProviderEvent::DirSize` и сразу появляется в колонке «Размер», если на экране всё ещё снимок того же поколения; отмена — через тот же `GenToken`.

## Модель данных

**Имена — WTF-8.** Имена из ОС хранятся байтами: UTF-16 переводится без потерь, непарные суррогаты кодируются трёхбайтовыми последовательностями, и обратное преобразование (`name::to_utf16`) восстанавливает исходные единицы UTF-16 точно. Корректный UTF-16 даёт корректный UTF-8, поэтому показ обычно идёт без копирования; замена на U+FFFD (`name::display`) применяется только при отображении. Имена Linux и WSL — произвольные байты.

**Листинг — один буфер имён и записи по 40 байт.** `Listing { names: Vec<u8>, entries: Vec<Entry> }`. `Entry` (`repr(C)`, 40 байт): размер, время изменения и создания (тики FILETIME), смещение имени в буфере, атрибуты, длина имени, длина расширения. Биты атрибутов: каталог, скрытый, системный, только чтение, ссылка (точка повторной обработки), диск, «размер известен», удалён. На запись нет отдельных выделений памяти.

**Стабильные индексы.** Записи только дописываются. Удаление ставит бит «удалён» (надгробие) и убирает строку из порядка, поэтому индекс записи не меняется за всё время жизни снимка. Выделение — битовая карта по индексам (`Vec<u64>`), фокус и якорь — индексы; всё это переживает сортировку и изменения.

**Снимок и вид.** `DirSnapshot`: поколение, путь, листинг, ключи сортировки, порядок (`Vec<u32>` — отсортированные индексы видимых записей), вид (`ViewSpec`: поле и направление сортировки, показ скрытых), признак завершения, ошибка, время. `DirView` держит `Arc<DirSnapshot>` (изменения применяются через `Arc::make_mut`, копия делается только если снимок ещё кем-то используется), выделение, фокус, якорь и лениво строящийся хеш имя → индекс.

**`FsPath`.** Нормализованные байты, длина корня и вид пути: `Computer` (виртуальный «This PC»), `Drive` (`C:\...`), `Unc` (`\\server\share\...`), `Verbatim` (`\\?\Volume{...}\...`), `Unix` (`/...`). При разборе `/` заменяется на `\` для путей Windows, `.` и `..` разрешаются лексически, `\\?\C:\` и `\\?\UNC\` сворачиваются в `Drive` и `Unc`. Путь с байтом NUL отвергается при разборе: Win32 обрезал бы его по NUL и адресовал бы другой файл. Относительный путь не является `FsPath`: его разрешает команда `Open` по `cwd`. `to_wide(true)` добавляет `\\?\` или `\\?\UNC\` для путей длиннее `MAX_PATH`. Родитель корня диска — «This PC».

**`Location`.** `Local(FsPath)` или `Wsl { distro, path }` с путём вида `Unix`; `provider()` даёт `ProviderId::Local` или `ProviderId::Wsl(distro)`. Каноническая байтовая форма — байты пути или `wsl://дистрибутив/путь`; при десериализации она проверяется, подделанный относительный путь отвергается. `Location::from_local` распознаёт `\\wsl.localhost\D\...` и `\\wsl$\D\...` и возвращает запрещённые в Windows символы из частной области U+F001–U+F07F; `to_windows` делает обратное (для имён не в UTF-8 — невозможно).

**Ключи естественной сортировки.** `SortKeys` строятся в том же проходе, что и листинг: общий буфер ключей, смещения и для каждого имени `u64` из первых 8 байт ключа. Кодирование (`encode_key`):

- ASCII-знаки препинания и управляющие — байт `0x02 + ранг`, ранги идут блоками по возрастанию кода (`0x00–0x2F`, `:;<=>?@`, `` [\]^_` ``, `{|}~`), то есть знаки раньше цифр и букв;
- серия цифр — байт `0x48`, длина значащей части (без ведущих нулей) и сами цифры, поэтому число сравнивается по величине;
- ASCII-буквы — `0x50 + номер буквы` без учёта регистра или `0x50 + 2·номер + заглавная` с учётом;
- остальные символы — UTF-8 строчной формы кодовой точки (первый байт не меньше `0xC2`), то есть после всех ASCII-букв в порядке кодовых точек.

Сравнение ключей как байтовых строк и есть естественный порядок; равные ключи разрешаются исходными байтами имени, затем индексом, так что порядок полный и детерминированный. `sort::sort` отбирает видимые записи, строит компактные элементы (группа «папка/файл», первичный ключ поля — размер, время со сдвигом знака или 8 байт расширения в нижнем регистре, затем два слова ключа имени) и сортирует их по целым числам; к полному компаратору обращается только при равенстве префиксов. Обратный порядок инвертирует целые ключи, папки остаются сверху. `insert_pos` и `find_row` — двоичный поиск тем же компаратором для изменений по одному.

## Окна и вкладки

Процесс — одна оконная система с любым числом окон. `Handler` (`crates/flit/src/app.rs`) хранит для каждого окна `App`, `Gfx` (текст и атлас), `Renderer` и диапазон видимых строк для отсева запросов значков.

`App` — состояние одного окна: вкладки и текущая вкладка, ширины колонок, редактор адресной строки, наведение и перетаскивание, кэши значков и названий типов, очередь эффектов, раскладка.

`Tab` — независимая вкладка: идентификатор, история (`History`: стеки «назад» и «вперёд» из `Location`), поколение, `GenToken`, `SnapshotSlot`, провайдер, за которым следит, `ViewSpec`, состояние загрузки, `DirView`, ошибка, очередь изменений, хлебные крошки, статистика, прокрутка и её цель, буфер быстрого перехода. Новая вкладка наследует вид текущей.

Вкладка помнит отдельно папку, которую загружает, и папку, чей снимок сейчас на экране (`view_loc`, меняется только вместе с `DirView`). Пока новый листинг не пришёл, Enter, двойной щелчок, Delete, Ctrl+Shift+C и запросы значков работают с той папкой, которую видит пользователь, а не с той, куда вкладка уже переходит.

**Глобальные идентификаторы вкладок.** Каждое окно получает базу `k · 2^32`, его вкладки нумеруются `база + 1`, `база + 2`, и так далее. События провайдера несут только идентификатор вкладки, и `Handler::window_of_tab` находит окно по диапазону; слежение (одно на вкладку) тоже не путает вкладки разных окон.

Закрытие вкладки отменяет её задания (`u64::MAX` в `GenToken`) и снимает слежение; закрытие последней вкладки закрывает окно; при уничтожении окна `App::shutdown` отменяет задания всех его вкладок и снимает их слежение, а обработчик отправляет получившиеся запросы провайдерам; при завершении сеанса Windows (`WM_ENDSESSION`) окна уничтожаются тем же путём, и состояние сохраняется; после последнего окна сохраняется состояние и цикл сообщений завершается. Новое окно (`Effect::NewWindow`) создаётся так: обработчик готовит `App` и ставит его в очередь, `Window::open_window` отправляет концентратору `WM_OPEN_WINDOW`, а `WindowHandler::created` забирает подготовленный `App`.

## Команда `Open` и единая точка маршрутизации

`Open { paths, select, target, cwd }` — одна сериализуемая структура для всех источников: её строит `parse_args` из командной строки, она же передаётся по каналу единственного экземпляра и её же собирает адресная строка. Пути остаются сырыми байтами WTF-8 и разрешаются в принимающем экземпляре вместе с `cwd` вызывающего процесса.

`parse_args` понимает синтаксис `explorer.exe`: путь, `/select,<путь>` (и `/select,` с путём в следующем аргументе, как его передают через пробел), `/e,`, `/root,<путь>`, `/n`, склейку ключей через запятую, игнорирует `/separate` и `/idlist`, а также `--new-tab`, `--new-window`, `--current-tab`. Пути Linux вида `/home/...` ключами не считаются.

`open::routes` превращает `Open` в маршруты `Route { folder: Location, select: Option<имя> }` и список ошибок. `resolve` по порядку: CLSID «Этого компьютера» → «This PC»; `shell:` и `::{` → `Platform::known_folder` (`SHCreateItemFromParsingName` и `SIGDN_FILESYSPATH`, поэтому годятся только папки с путём в файловой системе, иначе `UnknownShellLocation`); `file:///C:/…`, `file://localhost/C:/…` и `file://сервер/шара/…` (→ `\\сервер\шара\…`) с декодированием `%XX`; абсолютные, UNC и WSL-формы через `Location::parse`; формы Windows относительно `cwd`: `\x` и `/x` — от корня `cwd` (для `cwd` в WSL-шаре `/etc` даёт `wsl://D/etc`), `C:x` — от `cwd`, если он на том же диске, иначе от `C:\`; иначе путь присоединяется к `cwd`. Испорченный URL и голый `\\сервер` — ошибка `Invalid`, а не путь внутри `cwd`. Префиксы сравниваются по байтам, поэтому многобайтовые символы в начале пути не ломают разбор. `/select` даёт маршрут в родительскую папку с именем для выделения.

Одна команда открывает не больше 32 маршрутов, лишние отбрасываются с сообщением «Opened the first 32 of N locations». `App::open` подставляет вместо `OpenTarget::Default` значение `App::open_target` (пока всегда «новая вкладка», настроек в интерфейсе нет), вызывает `App::dispatch` и затем выводит первую ошибку разрешения в строку состояния той вкладки, которая оказалась текущей.

`App::dispatch(routes, target)` — единая точка, где маршрут становится вкладкой или окном:

- `NewWindow` → `Effect::NewWindow(routes)`;
- `CurrentTab` → первый маршрут в текущей вкладке (если вкладка уже в этой папке и нужное имя есть — только выделение, без перечитывания), остальные в новых вкладках;
- `NewTab` и `Default` → каждый маршрут в новой вкладке.

Через `dispatch` проходят входящие команды по каналу (`Handler::apply_opens` → `App::open`), адресная строка (`Effect::Open` с `CurrentTab` и `cwd` = текущая папка; обработчик вызывает `App::open` с тем же `Platform::known_folder`, поэтому `shell:`-пути работают и здесь) и внутренняя навигация: вход в папку, «вверх», хлебные крошки, новая вкладка, перетаскивание файлов. «Назад», «вперёд», обновление и `Rescan` не создают маршрутов и перечитывают папку через `Tab::load`. Командная строка самого первого процесса разрешается тем же `open::routes`, но маршруты открываются конструктором `App::new` — по вкладке на маршрут, а без маршрутов открывается сохранённая папка; ошибки разрешения показываются тем же `App::show_open_errors`.

## Провайдеры

Трейт `Provider { fn submit(&self, req: ProviderRequest) }` асинхронный: листинг возвращается через `SnapshotSlot`, всё остальное — событиями `ProviderEvent` в общий канал.

- Запросы: `List`, `Watch`, `DirSizes`, `Op { tab, id, op: FileOp }`, `Open { tab, path }`.
- События: `Changes`, `Rescan`, `DirSize`, `OpDone { tab, id, error, report }`. Операции оболочки несут вкладку-источник, поэтому `Handler::window_of_tab` доставляет ошибку в то окно и ту вкладку, откуда пришла команда.

`LocalProvider` лежит в `flit-platform` и не содержит кода ОС. `LocalProvider::new::<F, W, S>(fs, …)` обобщён по `Fs`, `Watcher` и `Shell + FileOps` и запускает потоки, которые владеют реализациями: пул чтения `flit-fs-N`, `flit-sizes`, `flit-watch-ctl` и `flit-shell-ops`. Сама структура хранит только отправители каналов и ожидающие постановки слежения, поэтому она не обобщена, а медленная постановка слежения (недоступная сетевая папка) задерживает только поток слежения, но не UI-поток. `flit-platform-windows` даёт реализации `NtFs`, `DirWatcher`, `ShellCom`. Тесты гоняют тот же код на файловой системе в памяти.

`NtFs` помечает запись ссылкой, только если тег точки повторной обработки — суррогат имени (`tag & 0x20000000`: символические ссылки, точки соединения, ссылки WSL); заглушки OneDrive и дедупликации остаются обычными файлами и папками. Тег берётся из `EaSize` при чтении каталога и из `ReparsePointTag` в уведомлениях.

`ShellCom` передаёт диалогам оболочки окно-владелец (только если на переднем плане окно самого Flit), а `ShellExecuteExW` — папку файла как рабочую. Значки, которые оболочка отдаёт крупнее запрошенного, уменьшаются усредняющим фильтром по предумноженным пикселям (`fit`). `ShellCom::open` и `FileOps::file_op` отказываются работать с путём, в котором есть имя, оканчивающееся точкой или пробелом: оболочка нормализует такой путь по правилам Win32 и молча срезает точку, так что удалился бы `build` вместо `build.`. Пользователь видит ошибку, а не удаление чужого файла.

Трейт `Platform` связывает реализации в одну точку: ассоциированные типы `WindowSystem`, `Renderer`, `Text`, `Fs`, `Watcher`, `Shell`, `Instance`, `IndexSource`, `Service` и функции `text`, `fs`, `utc_offset_minutes`, `dark_mode`, `state_dir`, `home`, `known_folder`.

**WSL в упрощённом режиме.** `Handler::submit` отправляет запросы `ProviderId::Wsl(distro)` в тот же `LocalProvider`, предварительно переписав все пути функцией `via_unc` в `\\wsl.localhost\<distro>\...`. Если путь нельзя выразить через шару (имя не в UTF-8), запрос дальше не уходит: `List` сразу получает снимок с ошибкой `Unavailable`, `Watch` снимает слежение, остальные запросы отбрасываются с записью в лог. Агент внутри дистрибутива, говорящий по протоколу провайдера из `flit-proto`, — следующий шаг; см. [docs/design/wsl.md](docs/design/wsl.md).

## Файловые операции

**Команды.** Каждая команда — отдельный публичный метод `App` в `crates/flit-core/src/ui/ops.rs`: `copy_selection`, `cut_selection`, `paste`, `rename_focused`, `new_folder`, `trash_selection`, `undo`, `redo`, `properties`, `context_menu`. Обработка клавиш (`ops_key`) только вызывает их, поэтому палитра команд может зарегистрировать те же методы. Команды работают с выделением той папки, которая на экране (`view_loc`), и строят пути Windows (`Location::to_windows`): папка WSL адресуется через `\\wsl.localhost`, а запрос всегда уходит провайдеру `ProviderId::Local`. В «This PC» вставка, новая папка и переименование отказывают с сообщением в строке состояния.

**Протокол.** `ProviderRequest::Op { tab, id, op }` несёт `FileOp`: `Trash`, `Copy { items, dest }`, `Move { items, dest }`, `Link { items, dest }`, `Rename { item, name }`, `NewFolder { dir, name }`, `MoveTo(пары)`, `Restore(пары)` и `Paste { dest }`; `id` — номер операции в окне. Ответ — `ProviderEvent::OpDone { tab, id, error, report }`, где `OpReport { op, items }` — фактически выполненная операция и пары «откуда → куда» для каждого обработанного элемента верхнего уровня: итоговое имя после переименования при конфликте, путь `$R…` в корзине. Частичный успех даёт и ошибку, и отчёт. `FileOp::map_paths` переписывает все пути операции, через него `via_unc` пропускает операции WSL.

**Выполнение.** Трейт `Trash` заменён трейтом `FileOps` (`file_op(&FileOp) -> OpOutcome`, `clipboard_files`, `clear_clipboard`). `ShellCom` реализует его на `IFileOperation` в потоке `flit-shell-ops`, по одной операции за раз. Собственный `IFileOperationProgressSink` записывает результаты `PostCopyItem`, `PostMoveItem`, `PostRenameItem`, `PostNewItem` и `PostDeleteItem`; в отчёт попадают только элементы из запроса, а не вложенные файлы папок. Флаги: корзина — `FOF_ALLOWUNDO | FOFX_ADDUNDORECORD | FOFX_RECYCLEONDELETE`; новая папка и копирование в папку самого источника — с `FOF_RENAMEONCOLLISION` (получается «x - Copy», как в Проводнике); остальное — со стандартными диалогами конфликтов и прогресса, владелец которых — окно Flit, если оно на переднем плане. Ярлыки (`Link`) создаются через `IShellLinkW` и `IPersistFile` с именем «x - Shortcut.lnk» и суффиксом « (k)», если имя занято. `Restore` перечисляет корзину (`FOLDERID_RecycleBinFolder`), находит элементы по путям `$R…` и вызывает у них глагол `undelete` — то же, что «Восстановить» в Проводнике. Проверка `shell_addressable` (имя, оканчивающееся точкой или пробелом) действует для всех путей операции, а новое имя не может быть пустым и оканчиваться точкой или пробелом.

**Вставка.** `Paste { dest }` разрешается в потоке операций (`run_op` в `LocalProvider`), а не в UI-потоке: `FileOps::clipboard_files` читает `CF_HDROP` и `Preferred DropEffect`. Вырезанное превращается в `Move` (элементы, которые уже лежат в `dest`, пропускаются), скопированное — в `Copy`. После успешного перемещения буфер очищается, но только если его содержимое не менялось с момента чтения (сравнивается номер последовательности буфера). Отчёт приходит с уже разрешённой операцией, поэтому отмена знает, что было сделано на самом деле.

**Буфер обмена.** `Effect::SetClipboardFiles { paths, cut }` исполняется в UI-потоке как дешёвый вызов Win32: `CF_HDROP` (`DROPFILES` с широкими путями) и зарегистрированный формат `Preferred DropEffect` (`DROPEFFECT_MOVE` для вырезания, `DROPEFFECT_COPY | DROPEFFECT_LINK` для копирования). Если буфер держит другой процесс, открытие повторяется до 20 раз через 15 мс. Ctrl+Shift+C по-прежнему кладёт пути текстом.

**Результат и выделение.** `App::op_done` выводит ошибку в строку состояния вкладки-источника, перечитывает вкладку WSL или UNC (живых уведомлений там часто нет), записывает отчёт в журнал отмены и, если результаты лежат в папке, открытой во вкладке, запоминает их имена (`Reveal`). Каждый кадр `ops_frame` ищет эти имена в `DirView` (они появляются по уведомлениям слежения), выделяет найденные, ставит фокус на первое и прокручивает к нему; для новой папки сразу открывается переименование. Ожидание длится не дольше 10 с.

**Отмена.** `flit_core::undo::Journal` — стеки отмены и повтора одного окна, до 100 шагов. `inverse(&OpReport)` строит обратный шаг: копия, ярлык, новая папка и восстановление → созданное в корзину; перемещение → `MoveTo` по парам в обратную сторону; переименование → обратно; удаление в корзину → `Restore` по путям `$R…`. Удалённое мимо корзины (в отчёте путь не изменился) вернуть нельзя: такие элементы пропускаются, а если других нет, шаг становится `Refuse` с сообщением. Операция, запущенная отменой, записывает свой отчёт в стек повтора, запущенная повтором — в стек отмены, новая операция очищает повтор. Журнал строится по фактическому отчёту, а не по запросу, поэтому имена, полученные при конфликте, учитываются.

**Переименование в списке.** `rename_focused` открывает `LineEdit` поверх ячейки имени: выделено имя без расширения (у папки — всё имя), ввод, вставка и IME идут в него. Enter и щелчок вне поля применяют, Esc отменяет. `validate_name` срезает пробелы по краям и точки и пробелы в конце, отвергает `<>:"/\|?*` и управляющие символы, зарезервированные имена (`CON`, `PRN`, `AUX`, `NUL`, `COM0`–`COM9`, `LPT0`–`LPT9`, включая `COM¹` и подобные, с любым расширением) и имена длиннее 255 единиц UTF-16; в папке WSL запрещён только `/`. Недопустимое имя оставляет редактор открытым с причиной в строке состояния. Если запись пропала из вида или пришло новое поколение листинга, редактор закрывается.

**Контекстное меню и свойства.** `Effect::ShellMenu` и `Effect::Properties` не исполняются прямо в обработке эффекта: окно кладёт запрос в очередь своего потока и отправляет себе `WM_SHELL_UI`, а меню строится уже без заимствования обработчика, потому что модальный цикл меню прокачивает сообщения того же окна. Меню собирается так: `SHParseDisplayName` → `SHBindToParent` → `IShellFolder::GetUIObjectOf(IContextMenu)` для элементов или `CreateViewObject` для фона папки, затем `QueryContextMenu` с `CMF_CANRENAME` (с Shift ещё `CMF_EXTENDEDVERBS`) и `TrackPopupMenuEx(TPM_RETURNCMD)`. `WM_INITMENUPOPUP`, `WM_DRAWITEM`, `WM_MEASUREITEM` и `WM_MENUCHAR` пересылаются в `IContextMenu3::HandleMenuMsg2` или `IContextMenu2::HandleMenuMsg`, поэтому подменю «Отправить», «Открыть с помощью» и значки расширений работают. Глаголы `rename`, `copy`, `cut`, `paste`, `delete` и `newfolder` (`SHELL_VERBS`) Flit забирает себе через `Event::ShellVerb`: они выполняются его командами и попадают в журнал отмены. Остальное выполняет `InvokeCommand` с `CMINVOKECOMMANDINFOEX`. Свойства — `SHObjectProperties` для одного элемента и `SHMultiFileProperties` для нескольких.

**Перетаскивание.** Вместо `DragAcceptFiles` окно регистрирует `IDropTarget` (`RegisterDragDrop`; `OleInitialize` один раз на UI-поток). Цель принимает только `CF_HDROP`, переводит координаты в клиентские и передаёт `DragEvent::Enter`, `Over`, `Leave` и `Drop` в `App::drag`, который возвращает эффект; картинку перетаскивания рисует `IDropTargetHelper`. Куда бросают: строка папки — в эту папку (строка подсвечивается), строка файла, пустое место и полоса прокрутки — в текущую папку, заголовки колонок и строка состояния — никуда, полоса вкладок и адресная строка — прежнее поведение (`Event::DroppedFiles`: открыть папку первого файла и выделить его). Эффект выбирает `choose_effect` по правилам Проводника: Alt или Ctrl+Shift — ярлык, Ctrl — копия, Shift — перемещение, без клавиш — перемещение в пределах тома (`same_volume`: тот же вид пути и тот же корень) и копия между томами, с учётом эффектов, разрешённых источником. Нельзя бросить папку в неё саму или в её подпапку и нельзя переместить элементы в ту папку, где они уже лежат. Бросок становится `FileOp::Copy`, `Move` или `Link`, то есть той же операцией с выделением результата и отменой. Перетаскивание из Flit начинается, когда мышь, нажатая на выделенной строке, сдвинулась на 4 пикселя: `Effect::StartDrag` через тот же отложенный `WM_SHELL_UI` вызывает `SHDoDragDrop` с объектом данных оболочки для выделенных путей (`GetUIObjectOf(IDataObject)`), поэтому приёмник получает все форматы Проводника. Щелчок по уже выделенной строке сужает выделение только при отпускании кнопки, иначе нельзя было бы перетащить несколько строк. Перемещение, выполненное приёмником, Flit видит через слежение за папкой.

## Единственный экземпляр

`main` до инициализации логов и до создания окна разбирает аргументы и вызывает `PipeInstance::acquire`. Именованный мьютекс `Local\flit-<SID>` определяет первичный процесс; первичный запускает поток, слушающий канал `\\.\pipe\flit-<SID>-<сеанс>` (`FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`). Канал создаётся с защищённым DACL `D:P(A;;GA;;;<SID>)`: открыть его может только владелец; если дескриптор безопасности не строится или первый экземпляр канала создать нельзя (имя заняли), слушатель пишет ошибку в лог и не запускается. Одновременно обслуживается не больше 4 клиентов (пятый получает `ERROR_PIPE_BUSY`), каждое чтение ограничено 2 с, а кадр — 256 КБ, так что молчащий или враждебный клиент не держит поток и память. Вторичный подключается к каналу с `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (сервер не может выдать себя за клиента), повторяя попытки до 3 с, и проверяет, что сервер канала (`GetNamedPipeServerProcessId`) запущен тем же пользователем: иначе имя мог занять кто-то другой, и процесс работает самостоятельно. Только после проверки он разрешает первичному вывести окно на передний план (`AllowSetForegroundWindow`), отправляет `Hello` и `Request::Open`, дожидается `Hello` и `Reply::Accepted` и завершается. Если переслать не удалось, процесс работает самостоятельно. У процесса с повышенными правами к именам мьютекса и канала добавляется `-admin`: обычный и повышенный экземпляры живут раздельно, и команда не пересекает границу UAC. В первичном процессе команда попадает в канал, будит цикл сообщений, применяется к активному окну через `App::open`, и окно активируется.

**Гонка с завершением.** Слушатель получает не `Sender`, а `OpenSink = Arc<Mutex<Option<Sender<Open>>>>` и отправляет команду и `Accepted` под этим замком. Когда закрывается последнее окно, обработчик под тем же замком забирает `Sender` и вычерпывает канал. Если там что-то есть, он возвращает `Sender` и открывает новое окно (цикл сообщений не выходит по `WM_QUIT`, пока есть окна). Если нет, состояние сохраняется и процесс завершается, а клиент, не получивший `Accepted`, запускается сам. Принятая команда не теряется ни при каком порядке событий. В режиме `--metrics` проверка пропускается. Чтобы пересылающий процесс не грузил ненужное, `flit.exe` загружает `d3d11`, `dcomp`, `dwrite`, `dwmapi`, `imm32`, `ole32`, `oleaut32`, `shell32` и `combase` отложенно (`/DELAYLOAD` в `crates/flit/build.rs`). Время жизни пересылающего процесса — около 28,5 мс против 24,1 мс у пустого `where.exe` на той же машине, то есть собственная цена Flit около 4–5 мс сверх `CreateProcess`; от входа в `main` до выхода — меньше 1 мс. Метрика «старт → первый кадр» отсчитывается от входа в `main`, поэтому после перехода на отложенную загрузку она выросла с 22–24 до 28–29 мс: загрузка графических DLL переехала из загрузчика внутрь измеряемого интервала. Полное время от `CreateProcess` до первого кадра от этого расти не должно, но отдельно оно не измерялось.
Подробности — в [docs/design/external-open.md](docs/design/external-open.md).

## WSL

Папка WSL — `Location::Wsl { distro, path }`, её принимают формы `wsl://D/путь`, `\\wsl.localhost\D\...` и `\\wsl$\D\...`. Хлебные крошки: «This PC › D (WSL) › …», родитель корня дистрибутива — «This PC». На этапе 1 файловые операции идут через 9P-шару `\\wsl.localhost` (`via_unc`): символы, запрещённые в именах Windows, видны как символы частной области Unicode, имена не в UTF-8 недоступны, живые обновления зависят от того, поддерживает ли шара расширенные уведомления. Подробности и план агента — в [docs/design/wsl.md](docs/design/wsl.md).

## Протоколы (`flit-proto`)

**Транспорт.** Кадр — длина `u32` little-endian и полезная нагрузка postcard, не больше 16 МБ (`read_frame_limited` позволяет задать меньший предел, протокол единственного экземпляра использует 256 КБ); длина проверяется до выделения памяти. Первый кадр в обе стороны — `Hello { magic: "FLIT", protocol, version, build }`, где `protocol` — `Index`, `Provider` или `Instance`. `read_hello` ограничивает приветствие 256 байтами и любой мусор (например, текст ошибки `wsl.exe` в UTF-16) превращает в `NotFlit`; несовпадение версий даёт `VersionMismatch` с версией и сборкой собеседника. Ошибки: `Io`, `Decode`, `TooLarge`, `NotFlit`, `VersionMismatch`, `Invalid`.

**Протокол единственного экземпляра** (версия 1): `Request::Open(Open)` → `Reply::Accepted`.

**Протокол агента-провайдера** (версия 1, на этапе 1 не используется): запросы `List`, `Stat`, `Watch`, `DirSizes`, `Op`, `Cancel`, `Shutdown`; события `Entries { batch }`, `ListDone`, `Stat`, `Changes`, `Rescan`, `DirSize`, `OpDone`. Пути в запросах — `FsPath`, проверяемый при десериализации.

**Протокол индекса** (`flit-search::proto`, версия 1, этап 2): `Query { gen, text, sort }`, `QueryDone { gen, total }`, `GetRows { gen, from, to }`, `Rows { gen, from, entries, dirs }`, `IndexStatus { volumes }`, `Error`. `flit-indexd` пока только печатает адрес канала (`\\.\pipe\flit-indexd`) и версию протокола.

**`EntryBatch`** — общий формат записей для всех протоколов: буфер имён и массив `WireEntry { name_len, meta }`. `entries(windows_names)` проверяет, что сумма длин (без переполнения) равна длине буфера и что имена не пустые, не `.` и `..` и не содержат `/` или NUL, а при `windows_names` ещё `\` и `:`, поэтому враждебный собеседник не может подсунуть путь вместо имени. Атрибуты вне `WIRE_ATTRS` (каталог, скрытый, системный, только чтение, ссылка) — внутренние биты вроде «удалён» или «размер известен» — отвергаются. `Event::validate(windows_names)` проверяет так же имена и метаданные в `Entries`, `Changes` и `Stat`; это обязанность того, кто примет события от удалённого агента. `append_to` дописывает пакет в `Listing`.

## Рендеринг

**Ядро строит, платформа рисует.** `App::frame(&mut Gfx<B>)` каждый кадр заново собирает `DrawList` — вектор экземпляров — только для видимой части интерфейса. Временные строки кадра (даты, размеры, типы) живут в арене `bumpalo`, которая сбрасывается каждый кадр. Платформенный `Renderer` умеет три вещи: изменить размер, загрузить прямоугольник в атлас и нарисовать `DrawList`.

**Один шейдер, один вызов отрисовки.** Экземпляр — 64 байта: прямоугольник, UV, прямоугольник отсечения (по `float4`), цвет RGBA8, радиус скругления, толщина рамки, вид (заливка, глиф, изображение). Всё рисуется одним `DrawInstanced(4, n)` полосой треугольников и одним шейдером `ui.hlsl`, который `build.rs` компилирует через `D3DCompile`, а результат встраивается через `include_bytes!`. Вершинный шейдер строит четырёхугольник по `SV_VertexID`; пиксельный отсекает по прямоугольнику экземпляра, рисует скруглённые прямоугольники и рамки через SDF со сглаживанием, глифы — по альфе атласа с кривой контраста, изображения — как RGBA с предумноженной альфой.

**Атлас.** Одна текстура RGBA8 2048×2048 для глифов и значков, упаковка полками с отступом 1 пиксель. Новые прямоугольники копятся в `Gfx::uploads` и загружаются `UpdateSubresource` перед отрисовкой. При переполнении атлас сбрасывается целиком вместе с местами значков: глифы растеризуются заново, значки загружаются из копий в памяти, а `App::frame` сразу строит кадр ещё раз, так что список примитивов со ссылками на старые места атласа на экран не попадает.

**Перерисовка только по изменению.** События и результаты рабочих потоков ставят флаг `dirty`, обработчик заказывает кадр, только если `App::needs_redraw()`. `App::frame` возвращает «анимация продолжается» (плавная прокрутка, непустая очередь изменений, сброс атласа, первые 300 мс загрузки), и тогда сразу заказывается следующий кадр. В остальное время цикл сообщений спит.

**Устройство.** Одно устройство D3D11 на процесс, общее для всех окон: `Renderer::device` создаёт устройство вместе с шейдерами и состояниями конвейера, `Renderer::new(device, window)` — swap chain и ресурсы окна. Устройства создаёт поток `flit-gpu` параллельно с остальным запуском: сначала программное WARP, затем аппаратное. Первый кадр рисуется на том, что готово раньше (UI-поток ждёт, только если не готово ни одно); когда приходит аппаратное устройство, окна, рисовавшие через WARP, пересоздают рендерер на нём, и программное устройство освобождается. Если аппаратное устройство создать не удалось, окна остаются на WARP.

**Swap chain и темп кадров.** Swap chain для композиции: `FLIP_DISCARD`, два буфера, `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT`, `SetMaximumFrameLatency(1)`; окно с `WS_EX_NOREDIRECTIONBITMAP`, swap chain выводится через визуал DirectComposition. Цикл сообщений для окон, ждущих кадра, вызывает `MsgWaitForMultipleObjectsEx` по их кадровым объектам ожидания вместе с вводом: ввод обрабатывается, пока ожидание не сработало, а кадр строится сразу после сигнала, поэтому отражает самый свежий ввод. Вывод — `Present(1, 0)` с вертикальной синхронизацией.

**Плавное изменение размера.** `WM_SIZE`, в том числе внутри модального цикла перетаскивания рамки, превращается в `Event::Resized`, после чего вызываются `ResizeBuffers` и синхронная перерисовка в том же сообщении: растянутых и пустых кадров нет. `WM_DPICHANGED` меняет масштаб, раскладка считается в физических пикселях.

Кадровый объект ожидания принадлежит рендереру (RAII-обёртка закрывает дескриптор); когда рендерер уничтожается, он убирает свой дескриптор из состояния окна, и цикл сообщений перерисовывает окно без ожидания, пока не появится новый. Контекст устройства привязан к потоку: рендереры создаются только в том потоке, где создан первый, и сами не `Send`.

**Потеря устройства.** Если любой вызов кадра (`Present`, `Map`, `GetBuffer`, `CreateRenderTargetView`, `CreateBuffer`, `ResizeBuffers`) вернул `DXGI_ERROR_DEVICE_REMOVED`, `DXGI_ERROR_DEVICE_RESET` или `DXGI_ERROR_DEVICE_HUNG` либо `GetDeviceRemovedReason` сообщает об ошибке, обработчик выбрасывает рендерер окна, для аппаратного устройства сразу создаёт новое (если не вышло, создаётся программное WARP, чтобы окно не осталось пустым) и заказывает кадр. Устройство пересоздаёт только первое окно, заметившее потерю: у окон есть номер поколения устройства, и остальные окна со старым номером просто перестраивают рендерер на уже новом устройстве; следующий кадр создаёт swap chain заново и сбрасывает атлас, так что глифы и значки загружаются в новую текстуру.

**Собственный заголовок.** Полоса вкладок занимает область заголовка. `WM_NCCALCSIZE` убирает стандартный заголовок (с поправкой на развёрнутое окно), `WM_NCHITTEST` спрашивает `App::hit_test` и отвечает `HTCAPTION`, `HTMINBUTTON`, `HTMAXBUTTON`, `HTCLOSE` или `HTTOP` для полосы изменения размера сверху. Благодаря этому система сама перемещает окно, разворачивает его двойным щелчком и показывает Snap Layouts над кнопкой «развернуть»; нажатия на кнопки заголовка приходят как неклиентские сообщения и переводятся в обычные события мыши для подсветки. Тёмный заголовок — `DWMWA_USE_IMMERSIVE_DARK_MODE`.

## Текст

Трейт `TextBackend` в `flit-core` — три синхронные операции: `shape` (строка и стиль → глифы с индексом шрифта, номером глифа, позицией и смещением кластера в байтах UTF-8, плюс ширина), `rasterize` (`GlyphKey`: шрифт, глиф, кегль в четвертях пикселя, субпиксельный сдвиг в четвертях пикселя → 8-битная маска покрытия) и `metrics` (подъём и спуск).

`DWriteText` на Windows:

- фабрика `IDWriteFactory2`; шрифт интерфейса — Segoe UI Variable Text, иначе Segoe UI; значки — Segoe Fluent Icons, иначе Segoe MDL2 Assets;
- раскладка через `IDWriteTextLayout` (подстановка шрифтов, двунаправленный текст, лигатуры, кластеры), которая «рисуется» в собственный `IDWriteTextRenderer`, собирающий прогоны глифов; шрифты интернируются в индексы, карта кластеров переводится в смещения UTF-8 для курсора и попадания мышью в адресной строке;
- растеризация через `IDWriteGlyphRunAnalysis` (`NATURAL_SYMMETRIC`, сглаживание в оттенках серого, текстура 1×1), четыре субпиксельные позиции по горизонтали; покрытие кладётся в атлас во все четыре канала.

`Gfx` кэширует разложенные строки (ключ — хеш строки и стиля, кэш очищается после 50 000 записей), глифы (`GlyphKey` → место в атласе или пусто для пробельных) и метрики шрифтов. Усечение с многоточием считается в ядре.

## Путь «ввод → кадр»

1. Оконная процедура переводит сообщение Win32 в `flit_core::input::Event`: клавиши — по коду виртуальной клавиши с модификаторами из `GetKeyState`, символы — из `WM_CHAR` с учётом суррогатных пар (символ отбрасывается, только если зажат ровно один из Ctrl и Alt, поэтому символы AltGr, то есть Ctrl+Alt, доходят до быстрого перехода и адресной строки, а сочетания Ctrl+A/C/X/V в адресной строке требуют Ctrl без Alt), мышь — в клиентских пикселях, неклиентские нажатия на кнопки заголовка — в обычные. Событие кладётся в очередь окна и тут же доставляется `Handler::event` → `App::on_event`.
2. `App` синхронно меняет состояние (выделение, фокус, цель прокрутки, текст адресной строки), ставит `dirty` и добавляет эффекты: запросы провайдеру, `Resort`, `Icon`, `TypeName`, буфер обмена, команды окна, заголовок, курсор, новое окно.
3. `Handler::flush` исполняет эффекты (отправка в канал или дешёвый вызов Win32) и, если нужно, заказывает кадр.
4. Цикл сообщений дожидается кадрового объекта ожидания и вызывает `Handler::redraw` → `App::frame`: забрать снимки, применить изменения в пределах 4 мс, сдвинуть прокрутку (экспоненциальное приближение к цели с постоянной 45 мс), разложить интерфейс, построить `DrawList`. Затем — загрузка новых прямоугольников атласа, отрисовка и `Present`.
5. Асинхронные результаты (снимки, события провайдера, значки, названия типов, сортировки) будят цикл через `WM_WAKE`; `Handler::woken` раскладывает их по окнам, и при необходимости заказывается кадр.

Значки: пока значка нет, рисуется глиф-заглушка и выпускается `Effect::Icon`. Ключ значка — расширение (общий значок типа), отдельный файл для `exe`, `ico`, `lnk`, `url`, `cur`, `ani`, папка или конкретный диск. Поток оболочки пропускает запрос, если строка ушла дальше чем на 32 строки от видимой области. Типовые значки и папки берутся из системного списка изображений (`SHGetFileInfoW` + `SHGetImageList`); его ленивую инициализацию `ShellCom::new` выполняет под общим замком, потому что при одновременном первом вызове из двух потоков `SHGetFileInfoW` возвращает 0 и значок типа навсегда остался бы заглушкой. Значки отдельных файлов и дисков — через `IShellItemImageFactory`. Название типа запрашивается один раз на расширение (`SHGetFileInfoW` с `SHGFI_TYPENAME`) и рассылается во все окна.

## Сохранение состояния

Файл `%LOCALAPPDATA%\Flit\state.bin`, формат postcard:

```
Saved {
    version: u32,
    persisted: Persisted { path: Location, view: ViewSpec, col_w: [f32; 3] },
    placement: Option<(x, y, width, height, maximized)>,
}
```

`col_w` — ширины колонок «Дата изменения», «Тип», «Размер» (имя занимает остаток). При загрузке отсутствующий, нечитаемый файл или файл другой версии заменяется значениями по умолчанию (домашняя папка, сортировка по имени, стандартные ширины); ширина колонки вне 24–4000 пикселей или не число сбрасывается к стандартной, а положение окна с неположительным размером отбрасывается. Снимок состояния берётся, когда окно закрывается командой закрытия: путь активной вкладки, вид, ширины колонок и положение окна. Записывается файл при уничтожении последнего окна: сначала `state.<pid>.tmp` (у каждого процесса свой, так что обычный и повышенный экземпляры не пишут в один файл), затем переименование поверх `state.bin`. При изменении формата увеличивается номер версии, миграций нет — старый файл просто игнорируется.

## Стратегия тестирования

- Тесты лежат отдельно от кода, в папке `test/` каждого крейта, и повторяют структуру `src/` (`src/ui/edit.rs` → `test/ui/edit.rs`). Исходный модуль подключает их строкой `#[cfg(test)] #[path = "../test/…"] mod tests;`, поэтому тестам по-прежнему доступны приватные детали модуля, а `cargo test` находит их без отдельных целей. Без фреймворков; criterion — только для бенчмарков (`benches/`).
- `flit-core`: перевод UTF-16 ↔ WTF-8 туда и обратно, включая непарные суррогаты; разбор путей (диски, UNC, verbatim, Unix, длинные пути); `Location` и отображение WSL, проверка при десериализации; разбор аргументов `explorer.exe` и разрешение путей; естественная сортировка (порядок из документации `StrCmpLogicalW`, числа, режимы регистра, некорректные имена); совпадение быстрой сортировки с полным компаратором на 3000 случайных записей; применение изменений к `DirView` (стабильные индексы, надгробия, слияние порядка, совпадение пакетного применения с полной сортировкой, выход невидимых записей из выделения); формы путей Windows и многобайтовые символы в `resolve`; отказ от слишком длинных корней; упаковка атласа и забывание мест значков при переполнении; курсор на границе символа и AltGr в адресной строке; кэш текста, многоточие и курсор с моноширинным тестовым бэкендом; форматирование размеров и дат.
- Интерфейс тестируется без окна: `App` с тестовым текстовым бэкендом получает синтетические снимки через `SnapshotSlot` и события ввода; проверяются навигация, выделение с клавиатуры и быстрый переход, сортировка и изменения, построение кадра и запросы значков, области заголовка, адресная строка, независимость вкладок, снятие слежения при закрытии, маршрутизация внешних команд и стартовых маршрутов, действия до прихода нового листинга, Delete без выделения, перерисовка после переполнения атласа посреди кадра, ограничение числа маршрутов, `App::shutdown`.
- Файловые операции в ядре (`test/ui/ops.rs`, `test/undo.rs`): проверка имён, уникальное имя новой папки, длина основы имени, правила эффекта броска; копирование и вырезание в буфер, вставка с выделением результата, отмена и повтор, отказ отменить удаление мимо корзины; F2, применение щелчком вне поля, недопустимое имя, переименование в папке WSL; новая папка с переименованием и её отмена; отказы в «This PC»; правый щелчок, глаголы оболочки, клавиша меню, Alt+Enter; порог начала перетаскивания и отложенный щелчок; броски с копированием, перемещением, ярлыком и запретом броска в себя; бросок на заголовок; обратные шаги для каждой операции и движение шагов между стеками журнала.
- `flit-proto` и `flit-search`: круговое кодирование каждого сообщения, враждебные кадры (огромная длина, обрыв, мусор), ошибки рукопожатия, подделанные пути, враждебные `EntryBatch` и события (внутренние биты атрибутов, `\` и `:` в именах Windows), ограниченные кадры.
- `flit-platform`: `LocalProvider` на файловой системе в памяти — потоковые отсортированные снимки, размеры подпапок, отмена, операции оболочки, разрешение вставки (вырезанное → перемещение без элементов из той же папки, очистка буфера), `via_unc`, недоступные пути WSL, слежение, поставленное до начала чтения. `flit`: очистка испорченного `state.bin`. `flit-core`: снимок старшего поколения не вытесняется младшим.
- `flit-platform-windows` на настоящей системе: DirectWrite (раскладка с кириллицей, растеризация, шрифт значков); разбор уведомлений слежения (последняя запись с именем в один символ, обрезанные и неизвестные записи); слежение, поставленное до возврата `watch`, и разворот коротких имён 8.3; теги точек повторной обработки; уменьшение значков до запрошенного размера; канал единственного экземпляра (пересылка через DACL владельца, отказ пятому клиенту, сброс молчащего клиента через 2 с, слишком большой кадр); файловые операции во временной папке (копирование, в том числе в ту же папку, перемещение, переименование, новая папка, ярлык, отказ для имён с точкой в конце, удаление в корзину и восстановление с уборкой служебного файла `$I…`); буфер обмена (разбор `DROPFILES` в широкой и ANSI-форме, запись и чтение файлов с эффектом через окно-сообщение с сохранением прежнего текста буфера); глаголы контекстного меню элементов и фона папки, пути в объекте данных оболочки.
- Производительность: бенчмарки `flit-core` и сквозной сценарий `--metrics` на данных `flit-gen` (`scripts/metrics.ps1` → [docs/metrics.md](docs/metrics.md)).
- CI: Windows (release-сборка, тесты, clippy), Linux (`cargo check --workspace` и тесты ОС-независимых крейтов), проверка правила зависимостей.

## Отклонения от ТЗ

1. **`TextBackend` находится в `flit-core`** (а `flit-platform` переэкспортирует его как `Text`): раскладке нужны синхронные измерения текста, а ядро не может зависеть от платформы.
2. **`Hello` вынесен из сообщений отдельных протоколов в общее рукопожатие транспорта `flit-proto` с магическим числом**: одно рукопожатие на все протоколы, и не-Flit собеседник распознаётся ещё до разбора сообщений.
3. **`Rows` протокола поиска несут `from` и используют общий `EntryBatch` плюс параллельный массив `dirs`**: ответ самоописателен для окна виртуального списка, а формат записей и его проверка одни для всех протоколов.
4. **Добавлен `OpenTarget::Default`**: отправитель не знает настроек получателя, поэтому куда открывать решает принимающий экземпляр по своей настройке.
5. **Обобщённый `LocalProvider` живёт в `flit-platform`, а не в `flit-platform-windows`**: это код без ОС поверх трейтов `Fs`, `Watcher`, `Shell`, он тестируется на любой системе, а `flit-platform-windows` даёт только реализации трейтов.
6. **Сортировка по колонке «Тип» идёт по расширению, а не по локализованному названию типа**: названия приходят от оболочки асинхронно, а расширение известно сразу и даёт детерминированный порядок.
7. **Естественная сортировка не зависит от локали** (ё после я, не-ASCII символы после букв) и не повторяет всех тонкостей `StrCmpLogicalW` с дефисами и апострофами: ключ вычисляется один раз на имя и сравнивается как байты, что быстро и одинаково на любой машине.
8. **Сглаживание текста в оттенках серого вместо ClearType**: одноканальная маска в общем атласе не зависит от цвета фона и порядка субпикселей монитора и работает с субпиксельным позиционированием.
9. **Смещение UTC читается один раз при запуске** (при создании окна), а не для каждой даты: форматирование дат в кадре обходится без системных вызовов; смена часового пояса или перевод часов учитываются после перезапуска.
10. **Названия типов получаются асинхронно, до ответа показывается заглушка «EXT File»**: запрос к оболочке может блокироваться, а UI-поток ждать не должен.
11. **Атлас глифов при переполнении сбрасывается целиком**: простейшая предсказуемая стратегия без учёта давности использования; при 2048² переполнение редко, а цена — один кадр перерастеризации.
12. **Пул потоков чтения фиксированного размера (4 потока)**: чтение папок упирается в ввод-вывод, четырёх параллельных загрузок хватает для вкладок и окон, автоподбора пока нет.
13. **Edition 2021**: чтобы `gen` оставался обычным идентификатором (в edition 2024 это зарезервированное слово).
14. **Канал единственного экземпляра — «сырой» именованный канал Win32 (`std::fs::File` поверх дескриптора) вместо крейта `interprocess`**: меньше зависимостей, протокол тот же.
15. **Неизвестные расположения оболочки без пути в файловой системе (Панель управления, Корзина) показываются как ошибка, а не передаются `explorer.exe`**: когда Flit назначен файловым менеджером по умолчанию, это грозит бесконечным циклом обработчиков.
16. **WSL на этапе 1 работает через `\\wsl.localhost`**: символы, запрещённые в Windows, видны как символы частной области Unicode, агента внутри дистрибутива пока нет.
17. **Платформа Linux — заглушки**: этап 1 нацелен на Windows, а заглушки держат workspace собираемым на Linux и проверяют, что ядро не зависит от Windows.
18. **Кэш листинга для холодного старта пока не реализован**: отложен; первые строки и так приходят потоково.
19. **Слежение использует только `ReadDirectoryChangesExW`**: расширенные уведомления сразу несут метаданные; сетевые шары и файловые системы без расширенной информации живых обновлений не получают.
20. **Первый кадр рисуется на программном устройстве WARP, затем окно переходит на аппаратное**: `D3D11CreateDevice` для аппаратного адаптера занимает на тестовой машине около 160 мс, а WARP готов за единицы миллисекунд; параллельное создание обоих упирается в блокировку загрузчика, поэтому `flit-gpu` создаёт их последовательно.
21. **«Ввод → кадр ≤ 1 кадр» проверяется как максимум не больше 1,5 периода обновления**: ввод приходит в случайный момент внутри периода, и даже идеальный конвейер с `SetMaximumFrameLatency(1)` показывает его в ближайшем кадре, то есть через время от 0 до 1 периода плюс выдержка композитора; полуторный запас отличает «следующий кадр» от «через кадр».
22. **Имена, оканчивающиеся точкой или пробелом, нельзя открыть или удалить в корзину**: оболочка Windows не умеет адресовать их без нормализации; листинг и навигация работают, операции оболочки отказывают с ошибкой.
23. **Короткие имена 8.3 в уведомлениях распознаются по форме** (`~` и цифры в конце основы не длиннее 8 символов, расширение не длиннее 3), а не по любому `~`: иначе файлы блокировки Office `~$x.docx` вызывали бы полное перечитывание папки при каждом удалении.
24. **Файловые операции адресуют файлы путями Windows и всегда идут через `ProviderId::Local`**: папки WSL — через `\\wsl.localhost`, пока нет агента; имена не в UTF-8 в таких операциях недоступны.
25. **Flit кладёт в буфер обмена только `CF_HDROP` и `Preferred DropEffect`, без `Shell IDList Array`, и принимает при вставке и броске только `CF_HDROP`**: этого достаточно для обмена с Проводником и большинством приложений; виртуальные файлы (`CFSTR_FILEDESCRIPTOR`: вложения почты, содержимое архивов) не принимаются, а уведомление «Paste Succeeded» источнику не отправляется. При перетаскивании из Flit используется полный объект данных оболочки.
26. **Контекстное меню, окно свойств и объект данных для перетаскивания создаются в UI-потоке**: `IContextMenu` привязан к окну-владельцу и его модальному циклу, поэтому расширения оболочки выполняются синхронно; это единственное место, где UI-поток ждёт сторонний код, и только по явному действию пользователя.
27. **Восстановление из корзины — глаголом `undelete` найденных в корзине элементов**, как «Восстановить» в Проводнике, а не переносом `$R…` через `IFileOperation`; служебный файл `$I…` при этом может остаться в `$Recycle.Bin`, корзина его не показывает.
28. **Операции выполняются по одной в единственном потоке `flit-shell-ops`**: долгое копирование задерживает следующие операции и открытие файлов, но прогресс и отмену показывает диалог Windows.
29. **Сообщения операций выводятся в строку состояния через ошибку вкладки** и держатся до следующей загрузки папки; отдельной ленты уведомлений и приглушённого вида вырезанных элементов нет.
30. **Журнал отмены знает только операции Flit**: команды контекстного меню, кроме `SHELL_VERBS`, и операции в других программах в него не попадают, а удалённое мимо корзины вернуть нельзя.
31. **Бросок на полосу вкладок или адресную строку сохраняет поведение этапа 1** (открыть папку первого файла и выделить его), а бросок на список копирует или перемещает.
